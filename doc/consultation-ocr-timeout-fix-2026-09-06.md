# 悬浮球图片 OCR 超时根因与修复

## 现场与因果链

用户在 2026-09-06 15:49 再次上传生日提醒图片，附件文件写入时间为 15:49:30，界面提示图片已保存但识别失败。该时段 sidecar 正在后台提炼；日志没有对应 OCR 完成记录。通过原有 Unix Socket 对同一原图发送相同 OCR 请求，25 秒内读不到响应头，现场复现超时。

`BackgroundProcessor._process_capture_group` 与 `_process_knowledge_extraction` 是异步方法，却直接调用 `InferenceQueue.submit_sync` 等待推理结果（最多 600 秒）。后台处理器和 OCR IPC 服务共用主事件循环，等待期间连接及 OCR 协程无法被调度；桌面读取超时为 20 秒。这是调度阻塞，不是图片本身无法识别。

上次修复移除了吞掉 OCR 错误的代码，但没有解决这个阻塞根因；仅在空闲时通过 Python IPC 重读图片，未覆盖后台提炼同时运行的场景。

## 修复

- 两条后台提炼路径通过 `asyncio.to_thread` 等待原有推理队列，保留 P1 优先级与队列治理，释放 IPC 事件循环。
- 单条提炼在实际执行线程中创建并关闭 SQLite 连接，避免把主线程连接传给推理线程。
- 附件错误保留连接/等待超时等具体原因，不再只显示通用识别失败。
- 重试按上次手工/截屏模式执行。手工图片咨询重试保留原问题和原附件，不再误走重新截屏。

## 验证

- 新增两条并发回归：故意挂住分组/单条后台推理，经过真实 TCP + 长度前缀 IPC 处理器发送 OCR 请求，要求后台完成前返回；同时检查 SQLite 在线程中可用。
- 后台处理、IPC 和悬浮咨询 Python 回归 77 项通过；Python 3.9.25 编译检查通过。
- 前端悬浮球、历史、API 回归 62 项通过，含首次 OCR 失败后点击重试恢复原问题与附件。
- Rust 常规 8 项通过；另有显式本地验收测试，调用与 WebView 相同的 `save_consultation_attachment` Rust 命令（包含 Base64 解码、落盘、真实 IPC 与 OCR）。
- 同一原图、后台提炼尚未结束时，真实 Rust 命令耗时 0.94 秒，返回 111 字符且包含“生日”；对应服务 OCR 日志为 910ms。验收只删除其自己生成的副本，保留用户原图。
- 前端构建和 diff 空白检查通过。开发运行时加载修复，未打包 DMG。

此处真实验收覆盖桌面命令到 OCR 的链路，未声称完成原生窗口鼠标点击的端到端自动化。
