## 排队诊断

直接调用繁忙的生产推理端点，两次短请求耗时约 21.8、21.97 秒，其中实际解码仅约 2.44、2.41 秒。日志显示请求与后台长提炼竞争单个推理槽位。

按应用交互优先级机制隔离后，相同短请求三次总耗时为 2.257、2.339、2.495 秒，首字延迟为 0.313、0.254、0.277 秒，未归因开销约 0.041、0.002、0.002 秒。非流式请求另测为 2.363 秒，排除了仅由流式模式导致差异的解释。原先约 19 秒差值主要是排队，不能当作模型计算耗时。

## MLX 与投机解码的验证条件

### 统一口径的长文本内存补测

此前 GGUF 主要缓冲区加总约 3.8 GiB，不能直接与 MLX 分配器报告的峰值比较，也不是完整驻留占用。本节替代该跨口径比较。

此前长文本设置为 16384 token 上下文上限，实际输入约 4K token，完整输出约 1.5K–4K token，没有填满 16K。此次四组使用相同输入（3997 token，SHA-256 相同），固定生成 2048 token，约占 6045 token 的序列长度。分别从全新隔离服务启动；单并发、最多加载一个模型，预热后执行一轮长文。后台提炼通过既有交互优先级锁让出资源。GGUF 8K 足以容纳这一样本，但不代表适用于更长的实际请求。

使用 macOS `proc_pid_rusage(RUSAGE_INFO_V2)`，每 200ms 汇总隔离 Ollama 服务及其子进程的 `ri_phys_footprint` 和 `ri_resident_size`。以下主表统一采用物理占用（physical footprint）；包含输入处理及生成阶段，驻留列为完成后保持模型加载、观察 5 秒的中位数。GPU/Metal 分配可能不完整反映在 RSS 中，因此不能仅根据 RSS 判断新引擎更省内存。进程树合计不等于整机内存变化，采样峰值也可能遗漏短于 200ms 的尖峰。

| 方案 | 上下文上限 | 生成阶段峰值 GiB | 生成阶段采样中位数 GiB | 完成后驻留 GiB | 解码 token/s |
| --- | ---: | ---: | ---: | ---: | ---: |
| 当前 GGUF / 0.30.8 | 16K | 4.87 | 4.87 | 4.78 | 46.52 |
| 当前 GGUF / 0.30.8 | 8K | 4.62 | 4.60 | 4.51 | 47.29 |
| 官方 MLX / 0.33.3 | 16K | 6.47 | 4.64 | 4.38 | 54.54 |
| 自建 MLX＋MTP / 0.33.3 | 16K | 7.19 | 5.34 | 4.67 | 62.00 |

相对 GGUF 16K，候选峰值增加约 2.31 GiB，生成阶段采样中位数增加约 0.47 GiB；完成后的驻留在本样本中相近，并非固定多出 241MB。相对普通 MLX，MTP 候选峰值增加约 0.71 GiB，完成后驻留增加约 0.30 GiB。此处仍然是整套候选对比，不是纯 MTP 消融。

权重包大小分别为 3,389,983,735 字节（GGUF）、3,973,305,013 字节（MLX）、4,214,505,733 字节（MLX＋MTP）。约 241MB 是 MTP 相对普通 MLX 的权重增量；整套候选相对当前 GGUF 的权重增量约 825MB。权重文件大小不等于运行内存。

GGUF 上限从 16K 降至 8K，峰值节省约 265MiB，未见明显速度损失；这是限制可用上下文换取缓存减少。测试中通过 `keep_alive: 0` 显式卸载后，隔离服务物理占用回落至约 17–54MiB，代价是下一次重新加载。没有修改正式配置的上下文或空闲卸载策略。

本轮速度与此前固定长度复测不同，说明 15% 不是固定收益；单轮内存测试不用于重新宣称稳定加速比例。质量不退化仍未得到证实，但也没有证据把既有错误归因于 MTP 本身。

数据和逐次采样保存在 [内存补测记录](evaluations/2026-09-05/memory-comparison/)，[复测脚本](evaluations/2026-09-05/memory_benchmark.py) 使用独立输出目录。四组测试全部完成，输入与输出 token 数一致；测试服务已停止，正式服务仍为 0.30.8。

### 运行时与模型构建

官方 0.33.3 macOS 压缩包已按发布摘要校验，包含完整动态库。新版二进制最低系统为 macOS 14，不能直接作为支持 macOS 12/13 客户端的统一替代包。

官方 `qwen3.5:4b-mlx` 对应 NVFP4 权重，但本次下载清单没有 MTP 头。不能把该标签本身视为已启用投机解码。官方 MLX 已在本机成功启动，日志确认 GPU 设备与完整动态库；本次未复现启动失败。

独立 MTP 候选从固定上游修订提取 MTP 权重。引擎检测到 MTP 后会给基础 RMSNorm 权重加 1，而官方 NVFP4 包中的基础权重已经偏移，不能直接拼接。第一版实验反向偏移后以 FP32 保存，虽保持数值，却会提升后续计算精度并增加开销；其测速作废，不作为 MTP 性能结论。修正实验改用上游原始 BF16 归一化权重，保持运行精度。所有实验均使用新摘要文件，未覆盖旧权重；候选是自建实验产物，不是官方发布版本。

81 个原始 BF16 norm 在偏移和舍入后，与官方预转换 norm 的最大逐元素差值为 0.03125。因此，候选与官方 MLX 的基础权重并非逐位一致，不能宣称这是对官方包数学上完全无差别的附加功能。应使用相同基础权重与精度做专门消融，才能量化 MTP 本身的净贡献。修正后短请求峰值内存从约 9.63 GiB 降至 4.19 GiB，说明第一轮构建问题确实影响运行开销。

0.33.3 的 MLX 实现遇到 Grammar 或 Logprobs 时禁用投机解码。产品 JSON 约束不能为了跑分去掉，因此 JSON 提炼主要验证 MLX 引擎收益；普通创作另查实际 drafted/accepted 日志和完整生成耗时。
