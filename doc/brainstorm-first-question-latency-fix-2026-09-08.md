可复现的长等待来自以下链路：

1. 前端串行等待技能匹配、保存会话和首题生成，却始终显示“正在梳理你的创作目标”。
2. Core 初始简报只是根请求的完整镜像，Sidecar 仍将它作为分支，重复执行关键词、向量与跨域重排检索。
3. 历史核对要求模型逐字生成引文。旧版原请求重跑实际出现“记忆摘录与召回原文不符”，随后耗尽 40 秒核对预算。该独立旧版探针未通过完整生产队列，最终 150 秒超时，不用它计算前后速度提升比例。

## 变更

- 仅在简报完全等于 Core 初始镜像时省略第二路检索，人工修改、答案和分支仍参与检索。
- 历史核对输出 `dimension_id + evidence_id`。程序从本轮受控片段恢复精确原文，再执行原有证据校验；保留当前用户意图、冲突和时间判断，未知 ID、截断候选、重复维度和矛盾混合字段均拒绝。兼容旧的 `memory_id + quote` 响应。
- 未发布问题中，内容不同但 ID 冲突的选项分配唯一编号；重复内容仍要求重生成。推荐排序及编号修正后，证据按已校验的唯一标签关联，避免引用串到另一选项。
- 首题及恢复卡片显示真实前端阶段和累计秒数，30 秒后提示久等。启动与恢复共用取消控制器，迟到响应不能覆盖新会话或清除新请求的加载状态。
- Sidecar 记录阶段/耗时/数量/异常类型；Core 记录安全会话标识、动作、成功/失败/取消及持久化阶段，不记录需求或模型输出。
