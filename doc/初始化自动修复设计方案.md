# 初始化自动修复设计方案

## 1. 目标

首次初始化遇到短暂网络失败、服务启动竞态、应用自有进程异常退出、迁移未完成或质检探针抖动时，程序应先执行有界、幂等、可审计的自动修复。只有自动修复用尽后才进入用户操作和诊断上报。

本方案不以“修复成功率”为理由破坏本地优先和用户数据安全边界。

## 2. 处理流程

```text
阶段执行失败
  -> 错误分类
     -> 可安全自动修复：记录 recovery -> 执行一次修复 -> 重新验证
        -> 成功：继续后续阶段
        -> 失败：标记 exhausted -> 显示精确建议 -> 允许重试/上报
     -> 不可安全自动修复：立即停止 -> 显示需要用户处理的原因
```

`recovery` 状态随初始化状态返回，包含 `status`、`action`、`attempt`、`max_attempts`、`error_code`和开始/完成时间。界面在 `waiting | running` 时显示“正在自动修复”，不提前要求用户点击。

## 3. 错误与修复策略

| 故障类别 | 自动动作 | 限制与最终处理 |
| --- | --- | --- |
| 下载中断、模型拉取抖动 | 使用现有断点和候选镜像重试；阶段额外重试一次 | 校验值仍必须通过，不执行未验证产物 |
| 本地 AI 引擎异常 | 仅在 PID、创建时间、可执行路径和模型目录均匹配时停止自有进程，然后重启 | 未知进程占用端口时不强制结束 |
| Core 启动较慢 | 先等待 10 秒启动宽限 | 宽限内恢复直接继续 |
| Core 退出或无响应 | sidecar 写入固定修复请求；Tauri 只停止它持有的 Core 子进程并重启；最长等待 45 秒 | 修复请求只能指向固定内置服务，不接受任意命令或路径 |
| Core 健康但迁移/读写检查失败 | 重启自有 Core 后重新执行完整性、表和临时读写探针 | 仍失败则保留数据库原文件并停止 |
| Skill/Tool 清单缺失或不一致 | 依照内置契约幂等重写清单，然后复检 | 不修改用户自定义 Skill 内容 |
| 质检失败 | 重新验证引擎、模型和数据库前置条件，再运行一次质检 | 仅一轮自动修复 |
| 固定合成冒烟探针抖动 | 清理探针临时数据后重试失败阶段一次 | 不读取、修改或上传用户内容 |
| 磁盘不足、平台不支持 | 不自动修复 | 给出可执行的用户处理建议 |
| 7070 被未知进程占用 | 不结束未知进程 | 返回 `CORE_PORT_CONFLICT` |
| 数据库真实损坏 | 不删除、不重建 | 保留原文件，修复用尽后允许上报诊断 |

## 4. Core 修复握手

1. sidecar 在它的受控状态目录原子写入 `backend-repair-core.request`。
2. Tauri 的 5 秒监督循环发现请求。
3. Tauri 只在自己的 `BundledBackendState` 中找到 Core 子进程句柄时才停止它，不根据 PID 文本操作外部进程。
4. Tauri 使用原打包可执行文件、HOME、日志和 IPC 环境重启 Core。
5. 新 Core 子进程启动成功后 Tauri 删除请求文件；sidecar 同时观察到请求被确认且 `/health` 返回带版本的 Core 响应，才判定修复成功。

## 5. 验收标准

- Core 较慢但在宽限内就绪：初始化自动继续，不显示失败。
- 应用持有的 Core 退出或卡住：自动重启后完成建库和质检。
- 网络或探针首次抖动：用户无需点击即自动重试一次。
- 未知程序占用 7070：不结束该进程，显示 `CORE_PORT_CONFLICT`。
- 数据库不可读：原文件字节保持不变，修复用尽后才允许重试或上报。
- 自动修复过程在界面可见，并在本地日志中记录阶段、稳定错误码、动作和结果，不记录用户内容。
