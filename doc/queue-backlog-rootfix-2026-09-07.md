## 实现边界

- 不删除采集记录、时间线或待烘焙内容；不手工推进水位、不清空队列、不重置历史失败统计。
- 错误契约先更新 `shared/bake-errors`，再更新 Sidecar 与 Core；`INFERENCE_QUEUE_BUSY` 必须同时满足 `scope=service`、`retryable=true` 才按服务级延期。
- 分段优化是计算复用，不跳过质量或证据检查。新知识门禁 prompt 尚有可合并的重复规则，但涉及模型行为等价性，不以简单删规则代替此次调度修复。
- 共享调度登记写入失败时，已取得槽的任务仍须交给 worker；取消/退出撤销就绪登记，失活进程租期回收，保证异常路径不泄漏执行槽。
- 单次长 P1 若超过 90 秒，等待的 bake 请求会收到服务繁忙；Core 在原 run 内有界退避并重新登记等待，不消耗候选失败次数。公平保证针对持续就绪的 P1/P2 优先级，不能据此承诺任意负载下固定完成时延。
- 时间线的 600 秒排队预算与 600 秒执行预算同样分离；排队到期不触发内容失败拆组。明确抢占信号和在线任务让位沿整个提炼链传播，避免内部捕获转为普通空结果。

## 实机观察发现的第二层问题

第一轮观察未达到净消化要求，因此没有把该轮改动当作最终结论：

1. capture 78305/78306 的主提炼只用 13.487 秒（6257 输入、532 输出 tokens），随后数据事实补提炼却耗费约 168 秒，因重复退化中止。P1 总执行为 181.659 秒。已增加仅含 data_facts 的闭合结构约束，先生成原文证据和值，再生成开放语义；保留本地 24 条合法事实容量，数值不得为空。连续 3 条完整对象的数值均不能回证时提前结束失效补提炼；截断时只回收完整对象并逐条验证。增加仅计数/耗时/状态的观测，不记录正文或响应预览。
2. P2 的 90 秒排队到期虽不再污染候选失败，但原 Core 会结束整轮，让后续 P1 工作片看不到 P2 等待需求。修为原 run 内原候选有界退避等待，开始请求前预留 410 秒；总预算不足才延期。文档合并同样覆盖，部分产物已保存时也必须传播服务级延期，避免错误推进水位。
3. P0 抢占/队列淘汰不再计为时间线内容失败。单条、合并、分段、契约修复、数据补提炼的内部异常捕获也统一透传调度异常，避免纯调度让位触发第二次失败拆单重算。
4. 同一数据补提炼输入经过两次隔离业务落库的实机对照，结构化请求均产出 3370 tokens 非法响应，耗时约 87–90 秒。第二次保留进程内结构诊断，确认不是 thinking 字段，而是正文包含 Markdown 围栏且无法解析为 JSON。请求中携带 schema 并不等于当前模型接口实际遵守 schema；后续必须以真实输出验收传输修复。

## 模型结构化输出的真实兼容问题

安装清单显示当前 Ollama 0.30.8 于 8/2 安装，属于已有运行时；声明源码 revision 为 `12e04379cd5a9a2f150104a02c5761213f4be777`，构建带 dirty 标记。该 revision 的 [chat 状态机](https://github.com/ollama/ollama/blob/12e04379cd5a9a2f150104a02c5761213f4be777/server/routes.go#L2736-L2760) 会先去掉具备 thinking 能力与 parser 的模型请求的 format，仅豁免另一类模型；[恢复约束的条件](https://github.com/ollama/ollama/blob/12e04379cd5a9a2f150104a02c5761213f4be777/server/routes.go#L2804-L2811) 又要求已输出非空 thinking。当前模型关闭 thinking，因此可能始终不启用 schema，与两次 chat 故障样本相符。此结论由本机元数据、对应源码和实测共同支持，不宣称二进制反汇编证明。

复用已有创作兼容路径，改用 [直接传 format 的 raw generate](https://github.com/ollama/ollama/blob/12e04379cd5a9a2f150104a02c5761213f4be777/server/routes.go#L622-L629)，并把已有 `creation.operations.decoding_schema` 抽到无服务初始化副作用的 `model_schema.py` 供两侧共用。解码时移除膨胀的 maxLength 与 maxItems>1；业务 schema 保持原样，数据事实 24 条、字段长度、逐字证据和 SOP 3–8 步继续本地校验。部分辅助标签数组原本没有独立条数校验，仍受输出预算和业务提示约束，不宣称所有数组都有新增本地硬上限。

第一次 raw 样本虽然是合法 JSON，却耗时约 178 秒生成 24 条空 value，全部被拒绝；加入更多嵌套长度限制后的样本又出现字段类型错误。两轮均不算通过。最终方案使用紧凑解码规则、单一事实对象 schema、证据优先与数值约束、无回证输出早停，而不是继续扩大复杂 grammar。

## 验证中修掉的兼容问题

跨进程公平的最终回归暴露 Python 3.9/macOS 的 monotonic 起点因进程而异；[Python 官方变更说明](https://docs.python.org/3/library/time.html#time.monotonic) 确认 macOS 从 3.10 起才统一。新共享租约改用公共时钟，本地执行 deadline 仍用 monotonic；新增 30 秒进程时基偏移、时钟回拨、失活租约回收回归，使用共享序号验证严格轮转。这是本次新调度逻辑在交付前修复的兼容缺口，不能倒推为用户此前积压的原因。

手工加载后出现的第二次 PID 替换也已核实：普通 nohup 子进程会被工具执行会话清理，桌面随后自动恢复；不是修复后的源码巡检仍在杀健康服务。用无害 sleep 对照验证独立进程会话可保持运行，最终加载采用该方式。
