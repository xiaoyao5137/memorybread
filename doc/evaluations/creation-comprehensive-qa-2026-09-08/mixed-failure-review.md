更早的 `delivery-repair-focused-v7.*` 使用了不同的 specialist 调用和生成参数，不能作为通用润色输入与专用修正输入的有效对照；记录保留，只作探索过程证据。后续验证须保持生产入口、原始材料和原有两次修正额度，并允许根据真实材料纠正旧误报，不能把旧报告当作事实来源或永不失效的拒绝依据。

同一问题记录传递后的第二次额度控制 `delivery-repair-second-budget-v8.json`（89.92 秒）仍未通过。输入是 v7 的真实剩余稿，并同时携带原失败和最新问题；原始模型输出与候选逐字相同，不是执行器将已改好的文本回退。复审此次正确找回“同事”问题，但又把已经去掉“本周”的正确“周三下午”误判成没有日期依据。该控制只证明旧问题能传入同一复审调用，不能证明修正执行有效，也不能认为历史判断天然可靠。仍需针对实际改动执行及历史问题与当前文本的区分继续验证。

原子补丁首次控制 `delivery-repair-atomic-patch-v9.json`（17.43 秒）仍失败：模型返回了删除协调流程的替换操作，但自行抄写 target 时漏掉 Markdown 行末两个空格，精确定位按预期拒绝，未写入文档。替换内容还保留了“各位同事”，所以即使位置正确也不能视为语义通过。后续从当前候选的实际片段枚举中选择目标，不将本次失败作为放宽空白匹配的理由。

细片段枚举的 `delivery-repair-bound-patch-v10.json`（125.07 秒）能正确应用两个补丁：将共同工作称谓改为中性参会者、删除协调要求。但它留下“如有特殊情况无法出席，”半句，人工判定不合格。两次复审分别存在通过项没有正文证据及重复检查 ID，最终被格式校验拒绝；原始判断还曾称后续行为缺失却可以直接发送，不能把它记为有效语义验收。此后生成修正的目标单位调整为完整 Markdown 段落，来源审计仍保留细片段，不以修改审计切分或业务词表清理来掩盖问题。

完整段落版本 `delivery-repair-paragraph-chain-v11.json`（228.27 秒）从原 v6 初稿开始，使用新实现完整走了原有两次修正额度，仍失败。第一轮删除完整额外流程并修正正文日期，第二轮修正时间标签；但第二轮对含“各位同事”的正文提交逐字相同的 replace，整体因另一处时间修改有效而接受，该称谓仍在最终稿。终审拒绝称谓，执行以未通过验收停止。历史解释还曾将已经删除的流程及已正确的“周三”误作当前问题。此控制证明段落单位和精确目标尚不足以保证所有问题都被执行，后续需核对具体问题与实际差异的对应关系，并减少历史长论证对当前核验的污染。

问题目录版本 `delivery-repair-issue-chain-v12.json`（23.58 秒）仍未通过，正文未变。模型对十个问题全部返回 `unresolved` 并附 `root_request` 来源，同时返回空补丁；执行校验禁止非来源处置附来源，因此拒绝该响应。该控制暴露解码 schema 允许了运行时禁止的字段组合，也允许明确存在的旧问题全部被推迟。后续需统一结构约束与执行校验，保留真实来源支持的误报纠正路径，不能将此结果记为实际修复。

组合约束修正后的 `delivery-repair-issue-chain-v13.json`（47.10 秒）仍失败。模型将十项问题均关联到 `conversation-user-0`，然后提交正文的同文替换；逐项 no-op 校验拒绝，未改变候选，也未进入新一轮审查。输入与来源完整，字段组合合法不能证明来源在语义上支持“同事”“本周”或报备流程。后续排查转向实际修正动作的输入顺序、重复候选与局部补丁提示，以及下层传输的上下文容量；不能把尚未证实的干扰因素记作已确认根因。

[独立传输核查](repair-transport-audit.md)确认客户端组装路径没有剪切 system 或用户消息；按完成时间和耗时关联的运行日志显示上下文 32,768、输入 3,350 token、输出 607 token，`truncated=0`。记录没有 wire 请求或服务端请求 ID，不能声称逐字传输哈希已验证，但没有证据将该次失败归因于输入截断或输出额度耗尽。
