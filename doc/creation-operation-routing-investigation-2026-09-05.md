# 创作会话 c8c30648：操作路由排查与根治方案

日期：2026-09-05。本文保留首次只读排查时的证据与设计。后续实现和验收见[通用操作执行交付记录](creation-operation-implementation-2026-09-05.md)；下文“未修改产品”描述仅指首次排查阶段。

## 结论

当前编排确有固定流程，叠加了原始需求对本轮操作的干扰。文档修订没有成为独立操作类型：删除章节进入全文修订，记忆搜索作为强制前置，普通“继续”重新开始路由。不能只改提示词或给“删除”增加一个特例。

应将会话目标、当前指令、文档操作、事实缺口和运行恢复分别建模，以操作的输入与依赖决定最小执行计划；工具启用表示允许使用，不表示必须执行。

## 根因定位

1. `ai-sidecar/creation/agent_loop.py::_compose_plan_from_decision`：非严格 Skill 分支只检查 memory_search 是否启用就添加它；末尾自动补全文撰写和模型质量审查。空决策不能表达“本轮无需这些能力”。
2. `ai-sidecar/creation/tools.py::ROUTING_CAPABILITIES` 与 `service.py::build_routing_prompts`：把记忆搜索定义为不参与路由的结构性能力。仅让模型“少选工具”无法取消它。
3. `agent_loop.py::_new_state`：修订时把 root_request 与“本轮补充”拼成 context_query，并用于需求分析和路由。路由提示没有结构化披露已识别操作、正文可用性、目标范围或待恢复运行。
4. `tools.py::fallback_routing_decision`：原始需求或 doc_type 出现“方案／设计／规划”等词即选择方案设计。两条修订指令因此都继承初稿的业务能力选择。
5. `agent_loop.py::_interpret_edit_intent`：普通修订统一返回 revise_document，找到章节也仅作为全文改写线索。已有 `_apply_document_patch(delete_section)`，但 writer 先处理所有 revision，后面的章节操作分支不能服务正常修订入口。只增加 delete_section 枚举也不够。
6. `desktop-ui/src/components/CreationPanel.tsx::runAgentTurn`：普通消息进入新一轮 Skill 解析和 Agent 请求。resume_state 在收到 model.request 后用于传回模型结果；`agent_loop.py::run` 也要求 pending_model_step 和 model_result。它不是用户“继续未完成任务”的持久化恢复协议。启动恢复同样重新调用 runAgentTurn。
7. 现有 inline-edit 有版本哈希、选区约束、幂等和撤销基础，但动作只覆盖脑暴、润色、扩充、细化；不能把普通对话删除直接接到当前接口而不扩展契约。
8. 当前进度主要是对话、正文与轨迹快照，不能可靠表达正在执行的操作及其已提交效果。此次缺失新轨迹进一步说明需要统一持久化运行状态，但缺失原因尚不能从现有记录确定。

## 目标设计

### 统一操作协议，先于 Skill 与能力路由

新增版本化 OperationRequest / OperationDecision。字段包括 instruction_id、session_id、operation_id、current_instruction、session_goal、base_revision、base_document_hash、target、constraints、context_requirements、resume_operation_id，以及可观测的 decision_source / reason_code。

操作类型表达通用能力，例如文档结构修改、局部内容变换、全文创作、资料获取、运行恢复。不要为本次章节名、业务主题或中文关键词建立业务分支。

客户端明确选区与动作可直接提交结构化操作。自然语言消息先用通用意图解析解析操作和目标；有唯一章节定位等可验证证据时可以直接执行。歧义或复合请求通过轻量结构化推理解析，不能以“简单”作为未经校验的判断。任意自然语言并不保证零次模型调用。

### 执行器与能力描述统一注册

每个执行器声明输入结构、适用操作、所需上下文、副作用、幂等方式和验证器。直接工具和复杂 Agent 使用同一能力注册机制，Agent 仅在需要生成或分析时被选中。

计划合成只校验权限、输入完整性、依赖和预算；移除“已启用就执行”“所有操作都补 writer/reviewer”的规则。保留必要校验，但优先使用确定性文档校验；没有语义质量问题时不追加模型审查。

记忆检索改为可选择能力。只有操作存在本地事实缺口时才执行；先使用当前正文、明确引用、已有产物。互联网和数据工具同理。降级基于当前操作及缺失输入，不能扫描整个原始需求来重新拼装复杂链路。

自动匹配 Skill 在操作确定后发生；对已生成文档的局部修改，历史 Skill 作为相关约束，不自动重跑初稿 workflow。用户明确要求重新执行 Skill 时才按其执行契约规划。

### 文档修改采用受控补丁

新增通用 document_patch 执行器，支持对结构节点或受校验范围删除、替换、插入、移动。复用 Core 的版本、哈希、幂等与撤销机制，扩大既有 inline-edit 契约或抽取共享服务。

章节定位采用支持代码围栏和层级的 Markdown 解析，返回稳定定位信息并校验匹配唯一性。删除包含子章节，但不删除下一个同级章节。不复用模糊字符串包含作为最终授权目标。

本例预期：解析删除操作 → 唯一定位“五、实施步骤与资源规划” → 删除整棵章节 → 验证其他正文未变化 → 原子提交新修订和可撤销记录。默认无检索、无方案设计、无全文重写。自然语言解析如需模型，调用范围仅限操作解释。

目录、编号和交叉引用属于显式派生依赖；有可确定修复方式则更新，无影响则跳过。确有语义影响才扩大到相关片段，不能因“可能联动”直接重写全文。删除范围内的数字、引用允许随章节删除，不沿用润色动作的事实保留规则。

### “继续”恢复操作及已提交效果

Core 持久化 operation/run 状态、原始待办指令、文档版本、节点输入输出引用、完成节点、未完成节点和提交结果。不要把密钥或供应商配置保存到 checkpoint。

“继续”首先解析本会话唯一未完成操作：有 checkpoint 则复用产物恢复待办；尚未生成 checkpoint 时，以已保存的原始操作恢复；没有唯一待办则根据当前上下文消歧。不得仅将“继续未完成的改造”当成全文写作目标。

文档补丁与操作完成状态在同一事务提交；请求重复返回已有结果。版本冲突不覆盖新正文，重新绑定或请求消歧。已完成的外部动作不重放；运行租约避免启动恢复与手动继续并发执行。

### 可解释且可核对的过程展示

保存并区分模型候选决策与实际执行计划；每项能力标注选择来源（显式操作、模型、依赖、恢复、降级）及必要原因。禁止把代码补入的全部步骤统一标为“模型决定”。

操作、运行、文档修订与事件以稳定 ID 关联；终态与提交结果一致。界面直接展示“删除章节”“恢复上次修改”等用户动作，不为一次补丁制造多 Agent 阶段。事件落盘需有连续序号与恢复策略，避免只有用户指令而没有对应运行证据。

## 实施顺序

1. 先固化 shared 操作、补丁、checkpoint 和错误码契约，覆盖歧义目标、版本冲突、无可恢复操作、重复提交。
2. Core 实现兼容的操作状态和原子提交接口，抽取现有 inline-edit 的通用约束；旧客户端请求保持兼容。
3. Sidecar 接入当前操作优先的解析与能力注册，移除无条件探针和全面改写兜底，接通受控补丁及持久化恢复。
4. 桌面普通对话、选区菜单和恢复入口统一消费操作协议；自动 Skill 解析后移，展示决策来源及真实动作。
5. 更新测试与文档，使用新旧路由对照记录评估，灰度后切换。不能用回滚到旧全流程掩盖精确操作失败；操作失败应返回明确状态。

## 验收门槛

- 本例删除：目标章节和全部子章节消失，未受影响正文保持原样；外部检索与 specialist 调用均为 0，全文生成调用为 0。
- 任意标题、同名标题、中文与英文、嵌套章节、代码块中的伪标题、目录和交叉引用均有测试；歧义不误删，缺失目标有明确结果。
- “不要删除”、删除并补充最新数据、全文重写、继续其他任务等反例不误入简单补丁；需要新事实时能正常选取资料能力。
- 在执行前、执行中、提交后响应前分别中断并恢复；成功产物复用，同一补丁只提交一次，版本冲突不覆盖。
- 已有文档来自 Skill 时，简单编辑不重复初稿工作流；显式重跑 Skill 仍生效。
- 路由空决策不被补入无关节点；降级不受原始需求“方案”字样污染。
- 回归现有创建、脑暴、Skill、选区编辑、质量审查、历史恢复和定时任务相关测试；按变更范围增补测试，Python 修改须通过 3.9 兼容性检查。
- 记录每类操作的实际能力次数、首个有效修改延迟、总耗时、恢复重复执行率和越界改动率；性能阈值依据改造前基线确定，不虚报提速比例。
