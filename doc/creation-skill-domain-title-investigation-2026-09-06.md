# 业务方案误选技术技能与文档标题污染：排查及根治方案

日期：2026-09-06。范围：只读排查与优化设计；未修改产品代码、技能数据或创作历史。

## 1. 当前事实

## 2. 根因

### 2.1 技能声明和执行行为不一致

本机 creation_skills.id=49，标题“技术架构方案评审文档模板”，稳定键 `creation-skill-general-solution-review-doc`。

- purpose/summary 是通用的“目标、现状、约束、方案设计、关键取舍、实施路径和验收标准”，没有限定技术架构。
- document_types 明确列出“方案评审文档、技术方案、业务方案、流程设计方案”。
- 实际执行步骤却要求总体架构、关键层级、独立组件、输入输出与依赖、配置等，并强制至少三个三级/四级子章节，每节至少 80 字。

名称已经技术化，描述仍覆盖业务方案，执行结构则按技术方案约束。模型不是凭空关联，而是接受了错误的适用范围和过于通用的用途声明。数据库现状不能单独证明是谁、何时修改了名称或步骤。

### 2.2 实际操作路由缺乏适用性校验

- `desktop-ui/src/components/CreationPanel.tsx:3205,3272`：通过 selectedSkillPayload(true) 披露所有已安装技能；selected_skills 此处实际上是候选目录，并不表示用户主动选中。
- `ai-sidecar/creation/service.py:3817`：本次使用统一创作操作解释器，决定 generate / execute_skill 等操作。
- `service.py:3863`：能力摘要仅展示标题、purpose 和 problems，未在此摘要中完整表达领域、产物边界和不适用条件。
- `ai-sidecar/creation/agent_loop.py:1102`：校验技能 ID 存在后即进入计划；没有校验“该工作流是否符合用户真正要的产物”。
- `agent_loop.py:1138`：模型选中的 primary 技能进入 strict_skill_workflow；变量 explicit_skills 并不等于用户显式选择。

因此，本次出现“提到了 SOTA → 技术与业务结合 → 通用方案结构相似 → 执行完整技术技能”的错误推导。SOTA 是业务方案可采用的手段，不能据此把主交付物改成技术架构评审。

旧的 `route_creation_skills` / `build_skill_match_prompts` 不是本次选中行为的实际入口，单改旧提示词不能修复此次链路。

### 2.3 程序直接把 Skill 名称作为文档标题

`agent_loop.py:4603` 的 `_strict_skill_document_title` 从 applied_skills 首项读取 name，只移除少数“创作方法/写作技能/Skill”后缀，随后返回名称。

`agent_loop.py:4784` 的 `_assemble_strict_skill_document` 直接拼接 `# {该名称}`，没有从用户需求或文档主题生成标题。

这不是单纯的模型命名失误。相同组装函数用于流式 `document.preview`（3552）、步骤结果处理及最终结构恢复（610）；只要求模型“不要使用技能名”仍可能被后续程序覆盖。最终结构恢复受 strict_skill_document_polished 等状态影响，并非所有结果一定被覆盖。

轨迹还出现 subsection_requirements_incomplete 触发的两轮技能质检复用，说明错误技能的章节约束已进入修订环节；不能仅凭这个错误码推断正文中每一段都不合适。

## 3. 根治设计

### P0：独立文档身份与命名契约

建立 document_title 与 title_source，来源优先级为：用户明确指定标题、本轮编辑应保留的现有标题、根据当前业务主题和交付物生成的新标题。技能名仅属于执行元数据，不是标题来源或回退值。

- 预览、组装、质检修复、最终保存、历史恢复与导出读取同一文档标题。
- 分步生成不能重复选择标题；用户改题时才更新并保留来源。
- 自动标题与已加载技能名、模板示例标题相同或仅移除包装后缀时，应重新命名；用户明确指定该字面标题时保留用户意图。
- 不以删掉“模板”后缀作为修复，也不从候选列表第一项生成名称。
- 标题失败时走有界重试或临时中性预览标题；最终提交前必须完成基于需求的命名校验。

本例合理标题为“快手灵机非 L0 商家增长与爆款视频运营方案”。这是建议标题，不是对当前运行记录的修改。

### P0：统一技能适用性契约与准入

先确定用户主交付物、目标读者、业务目标、约束和辅助能力，再判断候选能否满足该交付物。候选只可提供能力，不能反向改写主目标。

技能描述增加版本化、可配置的适用范围、排除条件、必要输入、交付物边界。路由输出选择来源（用户指定/自动选择/依赖）、匹配依据、冲突与缺失条件；自动选择只在适用性明确成立时进入完整工作流。证据不足时使用普通 generate，不强配“最接近”的模板。

适用性由模型语义判断，并由契约校验结构化结果和证据引用；不能声称字段校验本身可以保证语义正确。对边界案例设置评测和必要的独立适用性复核，不使用“包含 SOTA 就是技术方案”或“包含 GMV 就是业务方案”之类关键词分支。

区分 available_skills、explicit_skill_ids 与 routed_skill_ids，兼容迁移现有 selected_skills 字段，避免候选目录、用户选择与执行技能混为一谈。只有通过准入的技能才能展开步骤、约束和依赖。

### P1：修复现存技能数据与保存入口

将技术架构模板定位为技术架构设计与评审，校准其用途、产物类型、适用范围与步骤；业务增长方案默认普通生成，后续可提供独立业务增长技能，或经过验证的通用方案技能。不要只改名字掩盖技术结构。

编辑/导入/提炼/安装时校验名称、用途、产物和步骤是否矛盾。修改名称不应静默改写用户内容；可提示重新校准元数据。已有数据迁移按版本与内容指纹处理，备份旧版本、保留用户编辑、不全库重置；低可信矛盾技能暂不参与自动选择，仍允许用户查看和明确使用。

### P1：工作流与最终文档结构解耦

收集需求、行业调研、审校等是过程步骤，不天然等于最终文档章节。独立声明最终产物结构与步骤输出角色；组装器不能一律把步骤标题变成章节，也不能用技能名补全文档标题。技术要求不得因使用一个通用支撑能力而升级为整篇文档的硬约束。

### P1：可追溯与验收

按 session_id/run_id/instruction_id 记录候选与技能版本、选择来源、适用性结论、拒绝原因、标题来源及校验结果。遵守现有隐私边界，使用结构化原因、哈希和本地受控引用，不增加原始用户正文日志。

## 4. 必须通过的回归

| 场景 | 验收 |
| --- | --- |
| 本次商家增长原始请求，包含 SOTA | 主交付物仍为业务增长方案；不自动执行技术架构模板 |
| 同一业务请求去掉 SOTA | 技能选择和主交付物语义保持一致 |
| 明确要求视频生成平台架构、接口、容量与技术选型 | 可以选择适用的技术架构技能 |

| 标题技术化、描述通用、步骤强制组件化的旧技能 | 发现元数据冲突，不能无条件自动选用 |
| 没有匹配技能 | 普通创作完成，不强制选一个 |
| 用户指定文档标题或要求保留旧标题 | 所有生成、组装和恢复路径保留该标题 |
| 预览、分步重试、质检修复、最终提交、历史恢复、导出 | 同一文档标题不退回技能名 |
| 技能示例自带标题，或正常文档标题含“模板”字样 | 不复制示例；不误删用户有意指定的合法标题 |
| 仅改一段、删一章、继续未完成操作 | 不因新准入规则重跑整套技能或改标题 |
