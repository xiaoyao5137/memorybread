# 创作指令执行与资料充分性修复

## 问题与证据

此前为解决 c8c30648 一类“删除章节、继续未完成操作却走检索和方案设计”的问题，引入了按操作执行的路径。但将“移除默认业务流程”误当成了“模型没有选择检索就表示资料足够”，完整创作因此出现漏检索。

本次调查的完整创作记录为 history 139，session `creation-1788631971906-0647455dad0ea8`，run `run-d0201717-9020-45cb-bd87-b3f543fcc5c1`。需求是快手灵机吸引非 L0 商家、制作爆款视频、提升 GMV 并使用 SOTA 视频生成模型的方案。记录中 operation=generate，agents 只有 document_writer_agent，tools 为空；文档写作确实运行了，缺失的是资料获取和独立验收。基础检索能力已启用，并非工具不可用。

旧技能规则还存在“没有适用 Skill 就选择 generate”的过宽表述；已限定为新文档任务，编辑、回答与恢复按各自动作执行。

原实现的问题有三层：路由遗漏没有资料充分性检查；需求分析发生在选择之后，没有据此核对依赖；生成正文即可标记完成，缺少对事实和需求覆盖的验收。此前真实模型用例主要基于已有文档编辑，没有覆盖空白文档的完整需求，因而没有挡住回归。

## 本次修改

`ai-sidecar/creation/delivery_contract.py` 定义本轮输入需求和交付条件；`service.py` 提供模型调用入口；`agent_loop.py` 绑定必要来源、记录实际回执、核验产物并按具体问题有限修正。详细字段、事件与错误码见 `shared/creation-delivery/README.md`。

- 完整创作按具体资料缺口补选来源，不能未经检索便断言没有数据。
- 删除、替换、逐字追加等确定性补丁仍直接执行；恢复与撤销沿用指定历史操作。
- 语义追加只评估本轮内容，保留授权范围，不能因初始需求复杂就重走全文创作。
- 虚构、通用方法、已给齐资料的整理无需额外检索。
- 通过验收不自动润色；发现具体缺漏最多修正一次，然后再验收。
- 必要检索、审查或修正失败不能被节点容错吞掉。成功回执与证据充分是两回事。
- 后处理改变正文时核验实际落盘版本；局部二次修正仍绑定原始授权范围。

## 真实模型测试发现并修复的问题

第一版输入列表允许模型把不同来源压成一个条目。原始完整需求被全部塞入 work_context，漏掉业务数据与公开技术资料。已改成按已注册来源分别判断，每类允许无依赖，不强制检索。

第二个边界是模型把“没有收到真实数据”写成空输入列表，并以“说明缺少数据”代替真实复盘。结构化输出改称 requirements_by_source，明确它表示需要获取的资料，不是已收到的资料；不得降低原定验收标准。

另一个执行缺陷由局部修正回归发现：首次改写后节点 ID 改变，第二次修正不能再对新正文套用原节点 ID。现在完整修正补丁仍绑定本轮原始文档与原授权范围，保持范围外原文。

输入检查也需要完整正文，而不能只依赖零散行号映射。实际模型曾将“精简会议安排”误判为缺少会议资料；现在同时提供完整正文和可验证行 ID。来源判断先输出状态，再解释原因，避免先生成笼统背景需求再为检索找理由。没有按具体产品、章节名称或指令关键词写执行分支。

路由不再用动作分类器的概括替代原指令：概括可能丢掉章节位置，分类只提供操作类别边界。原指令放在历史材料之后作为当前执行依据，避免末尾旧章节覆盖本轮目标。

逐字操作与语义修改分别给出分类提示；局部执行器允许在补丁证据校验失败后纠正二者，不因一次模型分类错误锁死。动作到允许操作的映射由本地解码和执行边界共享，避免两条路径漂移。

混合指令按最终交付物分类；edit 的结构化输出不再允许跳到 generate，全文改写也可以通过覆盖全文范围的 transform 执行。“查数据后追加文档”属于局部修改，不能因为前半句是查询就转成仅回答。精确替换使用文本选择器；不能用包含后代内容的标题节点做整节点替换，否则改标题会误删正文。

用例区分已知项目和未明确项目两种输入：前者只需查询数据，后者允许先查私有上下文确认对象。二者都必须保留局部修改范围，不能扩成全文创作。这个区分来自输入信息是否充分，而非放宽所有追加指令的工具要求。

标题来源也按现有结构约束收窄：没有明确命名指令或现有标题时，仅允许 generated，不能让模型输出 user 后再因为无效来源反复失败。没有放宽原标题与技能标题的隔离校验。

数据检索自身的 data_query_planner 已由执行器合并进 data_search，不作为额外的全文 Agent 阶段。测试仅排除这类被实际执行器吸收的重复规划声明，仍禁止方案设计、全文撰写和全文审查混入局部操作。

验收输入将 provided_materials（用户提供的事实、原文、检索资料）与 candidate_document_lines（待审产物）分开。产物缺漏但输入齐备时进入 revise，不能把正文缺漏误判为输入缺失而 blocked。只有关键事实在所有输入中也不存在时才阻塞。

目标选择器允许有限修复 JSON 换行重复转义：原选择器若已逐字匹配原文，保持不变；只有还原后逐字匹配同一原文时才采用，还原失败仍报错。补丁新增内容不会被这项修复改变。

输入契约已确认自足时，验收输出仅允许 pass 或有具体修改要求的 revise，避免正文问题被误判为外部输入阻塞。仍只有一次修正机会，未通过时停止；不放宽事实与原文保留检查。

## 端到端补充修复

真实模型的追加用例发现结构化补丁仅约束 JSON 语法，仍可能出现多余动作字段。局部生成现已复用直接补丁的 JSON Schema，并使用确定性采样；字段、目标和范围校验仍作为最终边界。

模型验收最初要求逐字引用正文，小模型会改写引用或混入对证据的说明，造成无法验收。现在模型从实际正文行 ID 中选择支持证据，由代码还原原文，并校验所有验收条件。格式无效最多重试一次，不能降级为通过。写作和验收同时要求保留未明确展开的相对时间，避免凭空增加绝对日期。
