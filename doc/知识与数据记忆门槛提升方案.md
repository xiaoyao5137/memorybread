# 知识与数据记忆门槛提升方案

- 状态：首期已落地；第二期（知识复用半径维度化门禁）已完成实现与回放脚本，见第 15 节
- 更新日期：2026-09-07
- 决策阶段：change approval
- 适用范围：MemoryBread 本地自动提炼的“知识”和“数据”资产

## 1. 结论

不建议只调高一个统一的模型分数阈值。应把当前“候选通过后直接成为资产”改成四段式链路：

1. **事实保全**：原始 capture、timeline、逐字证据和系统观测时间继续保留，不因资产门槛提高而删除。
2. **类型路由**：先判断内容应进入知识、数据、文档、操作，还是只保留在时间线；禁止同一价值点同时生成知识和数据。
3. **分层晋级**：候选分为 `published`、`shadow`、`timeline_only` 三态。只有高质量候选进入用户可见资产；边界候选进入本地影子池等待复现、补证或用户确认。
4. **稳定身份合并**：数据按“规范来源范围 + 开放语义关系 + 业务对象 + 上下文 + 时间语义”合并；知识按“对象 + 谓词/结论 + 时间语义”去重，避免一次浏览产生多条流水账资产。

建议知识自动发布阈值先设为 `0.78`，`0.62–0.77` 进入影子池；数据不使用同一套“重要性分数”，而采用“开放语义事实门槛 + 不确定候选影子保全 + 稳定身份合并”。生产判定不得依赖预先列全的保护类型、噪声类型、指标允许列表或事实类型枚举；文中的具体类型和案例只用于解释与回放测试，不构成穷举规则。

> **2026-09-07 更新**：首期落地后的全量审计回放表明，单一 `match_score` 的 `0.78` 发布线
> 实际放行了 38.43% 的候选，且「代码」类发布率（65.12%）接近非代码类（32.71%）的两倍，
> 过程细节与关键事实拿到的分数几乎同分布。知识侧已改为**复用半径维度化门禁**
> （`knowledge-reuse-radius-v2`）：模型只判定不可替代性、复用受众、时效跨度三个维度，
> 发布分由 Core 确定性算出。上述 `0.78 / 0.62` 阈值降级为应急回退口径。详见第 15 节。

## 2. 问题与证据

### 2.1 当前知识门槛事实上未生效

候选预筛只要 importance 较高、用户验证、历史查看，或具备中高证据并命中特定活动/来源即可进入提炼。更关键的是，落库阶段的 `resolve_review_status` 当前忽略 `review_status`、`match_score` 和 `match_level`，固定返回 `auto_created`。Sidecar 即使把类型错配候选降到 `0.49 / low`，仍标成 `auto_created`。因此当前模型分数只被记录，没有成为发布门槛。

近期知识样本中出现了三类典型低价值资产：

- “用户查看/查询/复制了某页面”的活动流水账；
- 浏览器 JavaScript 提示、页面未加载等瞬时界面状态，被扩写成长期知识；
- 资产配置、成本、IP、CPU 等结构化事实同时进入知识和数据，形成跨类型重复。

### 2.2 当前数据更大的问题是“噪声行 + 来源碎片化”

数据侧已经要求对象、指标、数值和逐字证据，这是正确的可靠性底线。但现有校验允许“对象、场景、指标任一锚点命中证据”后继续降级修补，模型的 `high` confidence 也没有业务语义约束。结果是：数值真实存在，但可能只是待办数、已选数、消息时间戳、在线编辑人数等界面噪声。

同时，当前稳定身份仍容易被时间线切分影响。近期 60 条数据源全部只关联一个 timeline，平均每条关联 4.45 个 capture；其中 24 条来自同一规范文档 URL 且标题完全相同，却被拆成 24 个来源。

### 2.3 提高门槛时不能牺牲的内容

不能用有限枚举定义“重要事实”。只要一段信息同时满足以下开放语义条件，即使只出现一次、模型主观分数不高，也必须至少进入影子池：

1. 能形成一个可独立回答的未来事实问题，而不只是描述用户做过什么操作；
2. 丢失这段信息会让后续决策、执行、验证、追责或事实核对缺少不可替代的依据；
3. 对象、关系或属性、时态/适用范围和证据足以让系统在不补写、不猜测的情况下复述；
4. 当前没有另一条语义等价、证据质量不低于它的正式资产。

决策、状态、成本、配置、标识符、目标值等只是可能满足上述条件的示例，不是保护枚举。相反，某个看似普通的编号、时间或文本值，如果是恢复具体工作结果所不可替代的依据，也可能需要保留。

## 3. 用户与场景（Users and scenarios）

- **日常使用者**：希望“知识”和“数据”页只展示未来值得找回的资产，同时仍能从时间线追溯未晋级内容。
- **咨询/创作使用者**：需要精确事实、决策和约束能够被可靠召回，且目标值、阈值和实测值不会混淆。
- **本地质量维护者**：需要只在本机查看候选、证据、规则版本与原因码，回放新规则并安全回滚。

核心场景包括：从会议或聊天保留一次出现的关键决策；从报表保留成本与容量但过滤界面计数；把同一文档多次浏览聚合为一个数据源；把边界候选暂存在影子池并在补证后晋级。

## 4. 目标与非目标

### 3.1 目标

- G-001：知识有用率达到 AC-010 的 85% 以上，并降低活动流水账、界面瞬态和跨类型重复。
- G-002：不能形成可复用领域关系的偶发值进入数据正式视图的比例降至 AC-010 的 1% 以下，顶层重复率降至 5% 以下。
- G-003：对满足 2.3 开放语义条件的 grounded fact 达到 100% 保全；“未发布为资产”不等于“删除证据”。
- G-004：所有门槛决策可回放、可解释、可灰度、可回滚。

### 3.2 非目标

- 不删除原始 capture 或 timeline。
- 不在本方案中自动清理历史知识/数据；历史治理应先影子标注，再单独审批迁移。
- 不以“出现次数多”作为事实真假的判断。
- 不把供应商模型信息或私有内容写入外部遥测。

## 5. 功能需求（Requirements）：统一状态模型

每个候选先进入本地审计记录，得到以下状态之一：

| 状态 | 用户可见 | 用途 | 后续动作 |
| --- | --- | --- | --- |
| `published` | 是 | 高质量正式资产 | 正常检索、创作与刷新 |
| `shadow` | 否 | 可能重要但证据、语义或去重尚不足 | 30 天内等待复现、补证、关联任务或用户确认 |
| `timeline_only` | 否 | 活动轨迹、界面瞬态或无复用价值 | 仍可通过时间线与原始检索找回 |
| `rejected_invalid` | 否 | 无法回证、字段矛盾或明显幻觉 | 保留审计原因，不生成结构化资产 |

影子记录只保存本地结构化候选、证据引用 ID、规则版本与原因码；不复制无关正文，不上传服务端。

## 6. 功能需求：知识门槛

### 5.1 硬门槛

- **FR-001** — 知识候选必须表达至少一个可独立复述的“对象 + 谓词 + 状态/结论/约束”，并关联可回查的来源证据；“用户查看了/尝试了/点击了/复制了”本身不构成知识。
- **FR-002** — 系统必须先执行类型路由。若主要价值是“对象 + 指标 + 数值/配置”，则只进入数据；若主要价值是完整正文或步骤，则分别进入文档或操作。
- **FR-003** — 瞬时 UI 状态只有在明确造成持续业务影响、形成可复用排障结论，或被重复观测后，才可成为知识。单次 JavaScript 提示、加载失败、空输入警告默认 `timeline_only`。
- **FR-004** — 多主题活动汇总必须拆成独立事实；无法拆出具体对象和结论时不得发布知识。
- **FR-005** — 模型生成的事件时间必须逐字回证；否则只使用系统 `observed_at`，不得在详情中生成来源没有明确写出的日期。

### 5.2 评分与事实保全通道

> 本节是**第一期口径**（`knowledge-open-semantic-v1`），仅在 `bake.knowledge_gate_enabled=false`
> 应急回退时生效。第二期已改为复用半径维度化算分，见第 15 节；FR-006 / FR-007 的现行
> 定义以第 15 节为准。

第一期在通过硬门槛后按模型自报的 `match_score` 判发布：

| 维度 | 权重 | 评分要点 |
| --- | ---: | --- |
| 未来复用价值 | 0.30 | 能否支持后续决策、执行、排障或避免重复确认 |
| 对象与结论具体性 | 0.25 | 对象、状态、原因、约束是否明确 |
| 证据与归因 | 0.20 | 来源、说话人/系统状态、时间语义是否可回查 |
| 持久性 | 0.15 | 是否超越一次点击或短暂 UI 状态 |
| 新颖性 | 0.10 | 是否补充或更新现有知识，而非同义重复 |

第一期口径的实际问题是：这五个维度从未被逐项打分，最终只有一个模型自报的 `match_score`
承担全部权重，而模型对“过程细节”与“关键事实”给分几乎同分布（见 15.1 诊断数据）。

- **FR-006** — 第一期：分数 `>= 0.78` 才可自动发布；`0.62–0.77` 进入影子池；`< 0.62` 保留为时间线。**第二期（现行）**：发布分不再由模型自报，而由 Core 依据不可替代性、复用受众、时效跨度三个维度与时间线重要性确定性算出；`>= 0.72` 发布，`0.50–0.71` 进入影子池，`< 0.50` 保留为时间线，另有三条硬否决直接落 `timeline_only`。
- **FR-007** — `match_score` 或 `match_level=low` 不得被解析为 `auto_created`；Core Engine 必须成为最终确定性门禁，不能只信任 Sidecar 输出的状态字符串。**第二期补充**：模型只负责给出维度判定与语义身份，不得参与算分；`match_score` 从发布判据中移除，仅在应急回退口径下继续生效。
- **FR-008** — 候选未达到发布阈值、但满足 2.3 的开放语义条件时，系统必须进入 `shadow`，不得通过某个有限类型列表决定保留或丢弃，也不得使用更低的“特殊类型发布阈值”绕过统一发布门槛。
- **FR-009** — 用户手动确认、编辑、收藏或在创作中实际引用的影子候选必须可晋级；用户明确忽略的候选不得自动恢复。

### 5.3 知识原因码

门槛结果必须记录机器可读 `reason_code` 和人可读 `reason_summary`。`reason_code` 是允许后续新增值的命名空间字符串，读取方必须接受未知值；不得把一组固定原因码当作判定分支的完整枚举。`ACTIVITY_ONLY`、`ROUTE_TO_DATA`、`TIME_UNGROUNDED` 等只作为首批观测示例。

第二期新增的原因码（全部属于同一开放命名空间，读取方仍须容忍未知值）：

| reason_code | 状态 | 含义 |
| --- | --- | --- |
| `redundant_with_authoritative_source` | `timeline_only` | 用户自己的产出已在更权威载体里可原样查回 |
| `session_local_reuse_only` | `timeline_only` | 只在本次会话内对当时操作者有用 |
| `transient_process_detail` | `timeline_only` | 时效以小时计且非独占事实，过期后无追溯价值 |
| `reuse_semantics_incomplete` | `shadow` | 复用语义字段不齐，等待补证或复核 |
| `reuse_dimension_missing` | `shadow` | 维度取值缺失或无法识别，宽容降级而非硬拒 |
| `publish_score_met` | `published` | 复用半径算分达到发布线 |
| `below_publish_score` | `shadow` | 算分未达发布线但仍在影子区间 |
| `below_shadow_score` | `timeline_only` | 算分低于影子线 |
| `duplicate_semantic_identity` | `merged` | 近重复窗口内已有同语义身份条目，合并而非新增 |

## 7. 功能需求：数据门槛

### 6.1 行级事实门槛

- **FR-010** — 每个数据事实必须能独立回答“什么业务对象，在什么事实类型/维度/时期下，什么指标或属性，值是什么”。对象、值和关键维度必须在同一段连续证据中回查。
- **FR-011** — 数据事实必须保留来源表达的事实语气、时态和适用范围，使读者能区分“已经观测到的值”与“被要求、预计、假设或计划的值”；可以使用开放文本或结构化关系表示，但不得依赖一组封闭 `fact_kind` 枚举决定是否保留。
- **FR-012** — 一个值只有在其语义角色是某个明确对象的可复用属性、度量或关系时，才可发布为数据；如果该值只是在描述一次界面状态、交互位置或活动顺序，且脱离当次操作后不能回答具体领域问题，则不得发布为数据。实现不得依赖待办数、时间戳等词面黑名单，也不得依赖领域指标允许列表。
- **FR-013** — 只要候选满足 FR-010、其语义关系可回证、且没有等价正式资产，系统不得因低频、低主观重要性或值的形态不在预设列表中而丢弃；仍无法确定语义角色时进入 `shadow`。
- **FR-014** — 校验必须按行执行。一个来源中出现不满足 FR-012 的值时，只处理对应行，不得连带丢弃同批满足事实门槛的行。
- **FR-015** — `confidence=high` 只能作为模型自报信息，不能绕过确定性事实门槛。

### 6.2 数据身份与合并

- **FR-016** — `report_url` / 文档来源的稳定范围使用去 fragment、去非语义 query 后的规范 URL；同一文档不同 section 不得天然生成不同数据源。
- **FR-017** — 数据行的语义身份必须由规范来源范围、对象、关系/属性、适用上下文和时间语义共同生成；字段取值允许扩展，不得把事实类型写成封闭枚举。同一自然周内同一语义身份的新值更新同一快照，跨周保留阶段历史。
- **FR-018** — 同一规范来源下的多个指标应聚合为一个可浏览的数据集，数据行保持各自证据与来源 timeline；不得为每个时间线片段创建一个顶层数据源。
- **FR-019** — 无稳定 URL 的聊天/桌面来源仍按明确对象与指标隔离，禁止把不同话题仅因值或泛化标题相似而合并。

### 6.3 数据原因码

数据原因同样使用允许新增值的 `reason_code + reason_summary`，未知原因必须可存储、展示和统计。`INCIDENTAL_VALUE`、`MISSING_RELATION`、`UNGROUNDED_VALUE`、`MERGED_STABLE_SCOPE` 等只作为示例，不能反向成为封闭分类器。

## 8. 功能需求：重要事实不丢失机制

- **FR-020** — 任何资产门槛失败不得删除或改写原始 timeline/capture；审计记录必须保留来源 ID、规则版本、候选类型和原因码。
- **FR-021** — 影子候选出现新的语义证据、使用证据或用户反馈时必须重新评估；触发条件由“是否补足发布判断所缺信息”决定，不由一组固定事件枚举决定。
- **FR-022** — 任何已逐字回证、能形成独立事实问题、但分类或价值判断仍不确定的候选必须进入 `shadow`，而不是静默丢弃；后台可在空闲时补提炼一次。
- **FR-023** — 删除或降级历史资产前必须先验证其来源仍可回查；没有来源证据的历史资产只允许标记待审，不得批量硬删除。

## 9. 近期样本离线回放

### 8.1 样本与方法

本次只读抽取截至 2026-08-21 02:41 的最近 60 条知识，以及按创建时间倒序的最近 60 条有效数据源。首期实现完成后再次以只读方式确认样本集合和代表案例仍存在；历史记录没有新契约字段，因此分类数量沿用同一批人工语义标注，代码边界另由自动化测试验证，不把回放结果写回用户数据库。

知识样本按以下顺序判定：独立事实问题 → 类型路由 → 证据与不可替代性 → 统一评分分层。数据样本逐行判断“该值在语境中承担可复用领域关系，还是只描述当次界面/活动”，再按规范 URL 和稳定标题做保守合并模拟。回放没有使用类型允许列表、词面黑名单或特殊保护阈值。

### 8.2 知识回放结果

| 结果 | 数量 | 占比 | 说明 |
| --- | ---: | ---: | --- |
| 保留为知识 | 23 | 38.3% | 能独立支持未来执行、判断或事实核对，证据和语义完整 |
| 路由到数据 | 17 | 28.3% | 主要复用价值是对象属性、指标或状态值 |
| 路由到文档 | 2 | 3.3% | 主要价值来自成体系正文或资料集合 |

| 仅保留时间线 | 8 | 13.3% | 只描述当次浏览、切换、输入或多任务活动，不能形成独立事实问题 |

### 8.4 回放结论

近期样本支持“分类型门槛”而非“统一提高 importance”：

- 知识问题主要是发布门槛未执行和类型路由不足；
- 数据问题主要是 UI 数字没有业务语义门禁，以及同一来源被时间线切碎；
- 事实不应依赖模型的主观重要性或有限保护枚举，而应由独立事实问题、逐字证据、不可替代性和影子池共同保证召回。

## 11. 验收标准与追踪

- **AC-001** — 给定 `match_score=0.49`、`match_level=low` 的知识候选，执行发布决策后不得成为 `published`。覆盖 FR-006、FR-007。
- **AC-002** — 给定只描述“查看、查询、复制成功”的候选，且没有独立结论，结果必须是 `timeline_only/ACTIVITY_ONLY`。覆盖 FR-001。
- **AC-003** — 给定一次性页面 JS 提示，结果必须是 `timeline_only/TRANSIENT_UI`；给定同一提示造成明确持续业务阻塞且有排障结论时，允许进入 `shadow` 或发布。覆盖 FR-003。
- **AC-004** — 给定任意未预先定义类型的候选，只要它能形成独立事实问题、对未来任务不可替代、证据完整且没有等价资产，即使只出现一次也必须至少进入 `shadow`；删除所有类型特定保护分支后结果仍一致。覆盖 FR-008、FR-020、FR-022。
- **AC-005** — 给定若干值形态不同、领域不同的完整事实，以及词面相似但缺少语义关系的反例，系统必须基于对象—关系—值—证据判断，不得基于类型允许列表或值格式决定保留。覆盖 FR-010、FR-013。
- **AC-006** — 给定同一来源中一个可独立回答领域问题的值和两个只描述当次界面状态的值，系统必须逐行保留前者、将后两者移出数据正式视图；替换具体界面词后结果应保持一致。覆盖 FR-012、FR-014。
- **AC-007** — 给定来源分别表达“已观测、被要求、预计、假设”的多个值，保存和检索结果必须保留原语气与适用范围，不得把非观测值写成实测；加入一种实现未见过的新语气后仍可保存到影子池或正确展示。覆盖 FR-011。
- **AC-008** — 给定同一规范文档 URL 的 20 个时间线片段和不同 section fragment，系统只创建一个顶层数据源，同时保留全部合法指标行和来源 timeline。覆盖 FR-016、FR-017、FR-018。
- **AC-009** — 给定门槛失败候选，原始 timeline/capture 仍可按来源 ID 读回，审计记录包含规则版本和原因码。覆盖 FR-020。
- **AC-010** — 在人工标注的 grounded fact 集上，满足 2.3 条件的事实保全率必须为 100%；知识有用率不低于 85%，数据事实准确率不低于 95%，顶层重复率不高于 5%，非领域偶发值进入数据正式视图的比例不高于 1%。覆盖 FR-001–FR-023。
- **AC-011** — 给定以数值指标为主要价值的候选，系统只路由到数据；给定包含三个互不相关活动但没有独立结论的汇总，系统不得发布知识。覆盖 FR-002、FR-004。
- **AC-012** — 给定模型生成但来源未明确写出的事件日期，详情只展示系统观测时间；给定来源逐字写明的事件日期，允许保存为事件时间。覆盖 FR-005。
- **AC-013** — 给定影子候选，用户确认、编辑、收藏或在创作中实际引用后应重新评估并可晋级；用户明确忽略后不得自动恢复。覆盖 FR-009、FR-021。
- **AC-014** — 给定 `confidence=high`、逐字数值真实存在，但该值不能建立可复用对象关系的数据候选，结果不得发布；修改候选词面但保持相同语义角色后结果应一致。覆盖 FR-015。
- **AC-015** — 给定无稳定 URL 的两个不同聊天话题，即使标题或数值相似也不得合并；同一对象指标再次观测时允许触发影子重评。覆盖 FR-019、FR-021。

## 13. 风险与待决策

- **风险：重要但低频或新类型的事实被模型低估。** 通过开放语义保全条件、影子池和原始证据保全规避，不维护保护类型列表。

- **待决策 D-001**：影子池保留 30 天还是 90 天；建议先 30 天，满足 2.3 条件但仍待补证的 grounded fact 不自动过期。

### 15.2 维度契约

Sidecar 在 knowledge payload 中新增 7 个字段（`BAKE_KNOWLEDGE_PAYLOAD_SCHEMA`）：

| 字段 | 类型 | 取值 |
| --- | --- | --- |
| `irreplaceability` | 枚举，不可弃权 | `only_here` / `partially_recoverable` / `authoritative_elsewhere` |
| `reuse_audience` | 枚举，不可弃权 | `only_me_this_session` / `me_later` / `team_or_stakeholders` / `anyone_same_domain` |
| `validity_horizon` | 枚举，不可弃权 | `hours` / `days` / `weeks` / `months_or_more` |
| `source_publicity` | 枚举，不可弃权 | `own_work_only` / `publicly_documented` |
| `irreplaceability_reason` | 可空字符串 | 为什么这条信息不可（或可）从别处复原 |
| `subject_key` | 可空字符串 | 语义身份·对象 |
| `predicate_key` | 可空字符串 | 语义身份·谓词/结论 |

前三个枚举描述的是**信息自身的冗余度与复用半径**，`source_publicity` 描述的是**出处事实**，
都不是内容类目枚举。契约仍受 FR-008 约束：
Core 不得按时间线类目、`activity_type` 或关键词反推这些维度，未知取值必须宽容降级为
`shadow` 而不是硬拒。

`source_publicity` 与 `irreplaceability` 是两条正交的轴：前者问「公开世界有没有写过这句话」，
后者问「用户自己的产出有没有承载它」。四个取值组合各有含义，不得合并到一轴上二选一；
它引入的理由与实测见 §15.12。

正交性也决定了否决的触发条件：`source_publicity` 不进算分，只在**三个自报一致**时硬否决——
`publicly_documented` 且 `irreplaceability != only_here` 且 `reuse_audience == anyone_same_domain`。
单一轴自报不足以定生死，理由见 §15.12 的缺陷 2。

### 15.3 算分与两道与算分无关的准入条件

```
importance_score = (clamp(timeline_importance, 1, 5) - 1) / 4
quality = 0.40 * scope + 0.25 * audience + 0.20 * horizon + 0.15 * importance_score
```

| 维度 | 取值 → 分值（下标即半径档位） |
| --- | --- |
| `scope`（不可替代性） | `only_here` 1.0 / `partially_recoverable` 0.55 / `authoritative_elsewhere` 0.0 |
| `audience`（复用受众） | `only_me_this_session` 0.0 / `me_later` 0.5 / `team_or_stakeholders` 0.85 / `anyone_same_domain` 1.0 |
| `horizon`（时效跨度） | `hours` 0.15 / `days` 0.5 / `weeks` 0.8 / `months_or_more` 1.0 |

`audience` 与 `horizon` 的分值表和半径档位都从同一张有序取值梯派生（Rust
`KNOWLEDGE_AUDIENCE_LADDER` / `KNOWLEDGE_HORIZON_LADDER`，Python 镜像同名），避免算分表与
发布下限各写一份映射后失同步。

重要性取**时间线**的值而非知识 payload 的自报值，避免同一次推理自我抬分。

判定顺序（后者不得修改前者的结论）：

1. **硬否决 → `timeline_only`**：`authoritative_elsewhere`；`only_me_this_session`；
   `hours` 且 `irreplaceability != only_here`；`source_publicity == publicly_documented` 且
   `irreplaceability != only_here` 且 `reuse_audience == anyone_same_domain`（可关）。
2. **语义完整性 → `shadow`**：`future_question` / `decision_reason` / `evidence_summary` /
   `irreplaceability_reason` / `subject_key` / `predicate_key` 任一为空。
3. **维度可识别性 → `shadow`**：三个算分维度任一取值未知或缺失。
4. **确定性算分**：`>= 0.50` 才有资格往下走。
5. **发布下限**（仅算分过发布线时生效）：`reuse_audience >= team_or_stakeholders` 且
   `validity_horizon >= weeks`，任一不足则降为 `shadow`，reason
   `reuse_radius_below_minimum`。
6. 都不触发且 `>= 0.72` → 发布。

第 5 步是 §15.12 的缺陷 1 修复：受众与时效从「加分项」改为「发布的必要条件」。
第 1 步的第四条是缺陷 2 修复：公共参考知识从 `irreplaceability` 一轴上拆出来单独表达。

### 15.4 `partially_recoverable` 为什么回到 0.55

方案初稿给的是 `0.55`。实施中一度按「外部学术、理论、技术、科学知识也要纳入」的补充需求
上调到 `0.62`，理由是 `0.55` 会让这类知识在 `me_later` 受众下只得 `0.695 < 0.72`。
46 样本的无偏回放否定了这个上调（实测见 15.10），现已回到初稿的 `0.55`，发布线保持 `0.72`。
两个数都是方案原值，本轮改动不引入任何阈值偏离。

上调失败的根因是它**把区分度换成了刀锋校准**：`0.62` 时
`partially + team_or_stakeholders + weeks + imp 4` = `0.733`，只比发布线高 `0.013`，而这恰好是
本地 4B 模型的**模态输出组合**（38 条里 `partially_recoverable` 占 29、`team_or_stakeholders`
占 19、`weeks` 占 29），于是过程型结论顺着这条通道成批放行。

外部学术知识的正确发布通道是**受众维度**，不是抬高本档分值：提示词已要求领域公共知识取
`anyone_same_domain`，`0.55` 下 `partially + anyone + months + imp 3` = `0.745 ≥ 0.72` 仍然发布，
`imp 2` 得 `0.7075` 恰好落选——用户说的「**重要的**学术知识」这个限定词由时间线重要性兑现。
而 `partially + me_later` 是内部矛盾组合（领域公共知识不该判「只有自己后续会用」），真判成这样
的多半是把已被 commit 承载的过程结论误标为可部分复原，`0.695` 落 shadow 是正确结果。

下表是 7 条种子在 `0.55` 下的**实测**维度与算分（维度取自 15.10 的回放记录，非构造示例）：

| 种子 | 期望 | scope | audience | horizon | imp | quality | 结果 |
| --- | --- | --- | --- | --- | ---: | ---: | --- |
| 1206 会议故障复盘 | keep | only_here 1.0 | team 0.85 | weeks 0.8 | 4 | 0.885 | published ✓ |
| 4196 关键工作事实 | keep | only_here 1.0 | team 0.85 | weeks 0.8 | 3 | 0.8475 | published ✓ |
| 3804 关键工作事实 | keep | partially 0.55 | team 0.85 | weeks 0.8 | 5 | 0.7425 | published ✓ |
| 4270 过程细节 | block | partially 0.55 | me_later 0.5 | weeks 0.8 | 4 | 0.6175 | shadow ✓ |
| 4273 过程细节 | block | partially 0.55 | team 0.85 | weeks 0.8 | 4 | 0.705 | shadow ✓ |
| 4274 过程细节 | block | partially 0.55 | team 0.85 | weeks 0.8 | 4 | 0.705 | shadow ✓ |
| 4275 过程细节 | block | partially 0.55 | team 0.85 | months 1.0 | 5 | 0.7825 | published ✗ |

两个可直接读出的结论：

- `0.72` 落在 `(0.705, 0.7425]` 这个窗口里，正好把 3804（keep）与 4273/4274（block）分开，
  两侧余量 `0.0225` / `0.015`。`0.62` 时该窗口是 `(0.733, 0.7705]`，`0.72` 在窗口**下方**，
  所以三条反例全部漏过。
- **4275 在任何 `(scope, publish)` 组合下都无法与 3804 分开。** 两者 scope / audience / imp
  完全相同，只有 horizon 不同（`months_or_more` vs `weeks`），因此
  `score(4275) = score(3804) + 0.20 × (1.0 − 0.8) = score(3804) + 0.04` **恒成立**，
  任何单调阈值都不可能「发布 3804 同时拦下 4275」。要拦住它只能让模型改判维度
  （`authoritative_elsewhere` 触发硬否决，或把已提交验收的修复过程判到 `days`），
  这是提示词与模型能力问题，不是阈值问题。详见 15.10 的诚实结论。

`0.55` 还落在一个**平坦区**里：回放维度不变时，`scope` 取 `0.50 / 0.55 / 0.58` 在
`publish=0.72` 下给出完全相同的判定（16/38，种子 6/7），说明结论不依赖这一档的精确取值；
而 `0.62` 是整个 4×3 网格里最差的一格（24/38，种子 4/7）。

### 15.5 关键事实与外部科学知识的边界收紧

`authoritative_elsewhere` 是硬否决档，若定义过宽会把用户明确要求纳入的内容全部拦掉。因此
提示词把该档**严格限定为「用户自己的操作过程与产出」**（commit、CI 报告、工单状态、自己写
的原件）。外部世界本来就存在的公共资料（论文、技术文档、教程、行业报告、他人分享的原理与
方法）不是用户自己的冗余副本：即使原文仍可访问，未来要复原这条结论也得重新通读全文、重新
理解推导，属于 `partially_recoverable`，必须按知识沉淀。

据此，`BAKE_KNOWLEDGE_PROMPT` 与 `BAKE_BUNDLE_PROMPT` 的 accept 判据明确纳入两类内容：

- **可回溯咨询的关键事实**：某件事究竟是谁决定的、当时的口径是什么、对方给过什么答复或承诺、
  某个约束为什么这样定、某次重要沟通或会议得出的结论与待办归属。价值在于事后被问起时能原样
  回答，不要求它当时就推动了某个动作。
- **重要学术、理论、技术、科学知识**：论文与技术资料里的核心结论与作用机制、通用算法与设计
  原理、行业规律与方法论、可迁移到其他项目的技术判断依据。

配套维度写法约定：外部学术与技术知识的 `irreplaceability_reason` 应写明「原文虽在但需重新
通读全文才能复原该结论」；通用原理与方法论属领域公共知识，`reuse_audience` 通常取
`anyone_same_domain`；稳定原理、机制与已定责的复盘结论 `validity_horizon` 通常取
`months_or_more`。同时明确：这类资料被 `document` 收录**不构成** knowledge 的拒绝理由。

### 15.6 跨时间线语义身份去重

`dedup_key = sha256(normalize(subject_key) + "|" + normalize(predicate_key))[:32]`。

归一化规则：小写、剔除标点与空白、丢弃纯数字与 `v1`/`v2.3` 一类版本号 token；片段内
**不插入分隔符**（中文对象名本身不带空格，「联盟切流 共享集群」与「联盟切流共享集群」必须
收敛到同一 key）。

命中窗口内（默认 14 天）已有同 key 条目时，合并到最新一条（追加来源、写审计
`decision_state=merged` / `reason_code=duplicate_semantic_identity`），不再新增行。存量行
`dedup_key` 为 `NULL`，天然不参与匹配。

### 15.7 配置、开关与回滚

| preference key | 默认值 | 作用 |
| --- | --- | --- |
| `bake.knowledge_gate_enabled` | `true` | 置 `false` 走第一期单分数口径（ROLL-005 应急路径）。**实际效果已退化为 fail-closed，见下** |
| `bake.knowledge_publish_score` | `0.72` | 发布线 |
| `bake.knowledge_shadow_score` | `0.50` | 影子线；高于发布线时自动收敛到发布线 |
| `bake.knowledge_dedup_window_days` | `14` | 近重复窗口 |
| `bake.knowledge_min_publish_audience` | `team_or_stakeholders` | 发布所需的最低受众档位（必要条件）；取 `only_me_this_session` 等于关闭本规则 |
| `bake.knowledge_min_publish_horizon` | `weeks` | 发布所需的最低时效量级（必要条件）；取 `hours` 等于关闭本规则 |
| `bake.knowledge_public_reference_veto_enabled` | `true` | 是否启用 `redundant_public_reference` 硬否决（需三个自报一致，见 15.3） |

非法值（非数值、越界、非正数）一律回落默认值，不因配置错误让门禁失效。两个下限偏好是
枚举型：取值必须落在对应维度梯上，拼错或来自旧版本的取值（如 `long_term`）回落默认而不是
当成「无下限」——配置错误只应削弱严格性，不得放大成误拦。回滚只需写入
`bake.knowledge_gate_enabled=false`，无需回退代码或迁移；迁移 114 只新增可空列与索引，
对旧读写路径无影响。

**但这条应急路径的语义已经变了，必须如实说明。** `legacy_knowledge_decision` 读的是
`payload.match_score`，而第二期按 FR-006 把提示词里的全部数字锚点（含 `match_score`）删掉了，
模型不再输出该字段。46 样本回放里 `legacy_publish_rate = 0.0`，38 条语义齐备样本**全部**返回
`quality_score_missing` → shadow。也就是说置 `false` 现在的效果是**停止发布知识**（fail-closed），
而不是回到第一期行为。这对「门槛太低、垃圾知识淹没」类故障是安全的，但对「新门禁自身出 bug、
需要恢复旧口径」类故障无效——后者必须连同 `BAKE_KNOWLEDGE_PROMPT` 一起回退到第一期版本。
15.9 保留的 `match_score` 压低逻辑同理，只在提示词回退后才有意义。

### 15.8 存量治理边界

存量 4271 行 `bake_knowledge` 的 `dedup_key` / `quality_score` / `gate_rule_version` 全部为
`NULL`，2925 条已判定审计的规则版本全部是 `knowledge-open-semantic-v1`。第二期门禁只在烘焙
当时生效，**不回补重算**，因此存量资产不会因本次改动被降级或隐藏，符合 ROLL-002。

v3 把「存量」的边界往前推了一批：本次上线前已经按纯算分判定的行（实测今天 50 条已发布知识
都是 `knowledge-reuse-radius-v2`）现在也算存量，**同样不回补重算**。这也是判定语义变化时升
版本号而不是原地改 v2 的原因：不升版就无法把「需要重判的那批」与修复后新判的行区分开，
事后也就量不出修复效果。是否要按 v3 重判并降级这批行，属于改变原「只影响新增」决策的
动作，需用户明确确认后单独执行。

### 15.9 错配守卫的适配

Sidecar 原有的 `template_like_content` / `sop_like_content` 两条 knowledge 错配守卫只靠把
`match_score` 压到 `0.49` 生效。第二期门禁不再读 `match_score`，这两条守卫会**静默失效**，
成型模板与多步操作流水将被当成知识发布。已改为同时降级复用半径维度：`irreplaceability`
置 `authoritative_elsewhere`，`irreplaceability_reason` 点名同批次的 design / sop 资产为权威
载体并附 `| mismatch_guard=<reason>` 标记，从而走硬否决落 `timeline_only`。`match_score`
压低逻辑保留，以兼容应急开关回退到第一期口径。

### 15.10 离线回放与验收

`ai-sidecar/scripts/evaluate_knowledge_gate.py`（只读，连接串固定 `mode=ro`，不含任何
DDL/DML，不写回用户数据库）：

- `--mode static`：从审计 `shadow_payload_json`（完整快照）或 `bake_knowledge.content`
  （部分键）回放，输出**全量审计口径的基线**（15.1 的数据即由此产出）。
- `--mode replay`：用当前 `BAKE_BUNDLE_PROMPT` 对同一批时间线重跑一次提炼，拿到维度后算
  两套门禁，这是验收线的评估口径。
- 种子标注集内置用户点名的 4270/4273/4274/4275（应拦）与 3804/1206/4196（应留），可用
  `--expect-keep` / `--expect-block` 扩充到约 40 条。

#### 取样框必须是审计表

第一版脚本从 `bake_knowledge` 取样，跑出来的发布率是 **69.44%**，看上去像“新门禁比旧门禁
还宽松”。真实原因是取样框有偏：`bake_knowledge` 只收录已发布的行，shadow 与 timeline_only
候选根本不建条目，因此框内 43 个样本的 `recorded.decision_state` **全部是 `published`**。
这样测出来的是「旧门禁已发布内容的留存率」，不是整体发布率，与 15.1 的 38.43% 基线不可比。

改为以 `bake_artifact_audits` 为取样框（三种结局都留痕，与 `load_baseline` 总体口径一致）后，
近 60 天 40 条 + 7 条种子共 46 个样本的构成为 23 published / 22 shadow / 1 timeline_only，
与基线比例吻合。shadow 候选没有知识条目，其 capture 上下文按 `captures.timeline_id` 反查，
与烘焙流水线取上下文的方式一致。`tests/test_evaluate_knowledge_gate.py` 用一个同时含已发布与
shadow 候选的最小库把这个偏置固化成断言，避免以后再退回有偏取样框。

验收线：种子正例全部保留、反例全部拦下；整体发布率从 38.43% 降到 15%–25%；「代码」类发布率
与非代码类加权发布率的差值不超过 15 个百分点（`code_category_not_outlier`）。

Python 侧 `tests/test_evaluate_knowledge_gate.py` 把 Rust 测试已验算过的判定表固化成镜像断言：
任一侧改了分值、权重或 reason_code 而另一侧没跟上，测试即失败，避免离线评估结论与线上判定背离。

1. **发布率 0.4211 仍高于 15%–25% 目标带**，`publish_rate_in_target_band = false`。

2. **三条硬否决在 38 条实测样本中一次都没触发**：`authoritative_elsewhere` 0/38、

   `weeks` 29/38 的模态组合，门禁退化为「在单一维度组合上按时间线重要性做筛选」。
   **这是本次改造最大的未解决项**，属推理能力议题，需单独跟进。
3. **`legacy_publish_rate = 0.0`：应急开关已退化**，详见 15.7。

5. 46 样本里 4 条 `replay_error`（LLM 输出无法解析）、4 条缺 `evidence_summary`，

### 15.11 本地推理不执行 schema：取值集合必须由提示词声明

第二期把三个维度设计成封闭枚举，原本打算靠 JSON Schema 的 `enum` + `required` 在解码阶段
强制取值。实测否定了这条路径——同一 schema 以五种方式下发，输出逐字节相同：

| `format` 下发方式 | 实际输出 |
| --- | --- |
| schema dict（生产用法） | `{"timeframe": "数周或更久"}` |
| schema 的 JSON 字符串 | 同上 |
| `"json"` | 同上 |
| OpenAI `json_schema` 包装 | 同上 |
| 不传 | 同上 |

环境：Ollama 0.30.8 + `qwen3.5:4b`，`temperature=0`。键名与取值都不符合 schema，说明
`format` 被完全忽略，grammar 约束没有生效。回放中模型自创 `weeks_or_more`（7 条里 2 条）
正是这个原因，与提示词写得好不好无关。

由此得到三条设计结论：

1. **Core 的宽容降级是承重结构，不是兜底装饰。** 维度取值未知或缺失一律判
   `reuse_dimension_missing` → shadow 并保留完整 payload 快照，是这条链路上唯一可靠的防线。
   既不能改成硬拒（会直接丢数据），也不能改成猜一个近似值（会把模型的自创取值洗白成合法判定）。
2. **取值集合必须在提示词里逐字列出。** `BAKE_KNOWLEDGE_PROMPT` 现在显式声明三个维度是封闭
   集合，并点名禁止 `weeks_or_more` / `long_term` / `internal_team` 这类自创值；
   `validity_horizon` 原先只提到三个取值（`weeks` 从未出现），模型只能自创近似值，现已补全四档。
3. **`BAKE_KNOWLEDGE_PAYLOAD_SCHEMA` 的 `required` 保留，但当前只作契约声明。** 它眼下不产生
   约束力，一旦换用支持结构化输出的模型或推理栈即刻生效；同时它让 Python 侧测试能断言
   「三个维度不可弃权」，与 Core 的 `Option<String>` + 宽容降级形成双向锁。

这是既有的平台状况，不是第二期引入的回退：同一原因也解释了生产日志里
`bake bundle recovered independent artifacts ... reason=invalid_json` 的片段恢复分支为何会被
触发。修复它属于推理栈议题，不在本次门禁改造范围内，但会直接影响门禁的实际拦截精度，需单独跟进。

### 15.12 用户点名第二批（4341–4350）暴露的两个缺陷与修复

用户复查知识页后点名「最近生成的这些知识，也都是不重要的」，取样框是今天 13:18–13:49
生成的 ID 4341–4350。顺着这批行回查判定链路，确认两个缺陷，本轮都已修复；规则版本随之从
`knowledge-reuse-radius-v2` 升到 `knowledge-reuse-radius-v3`。升版本而不是原地改 v2 的判定，
是为了把今天已按 v2 发布的行与修复后的判定区分开——否则量不出修复效果。

#### 缺陷 1：受众与时效只是加分项，不是发布条件

加性公式下 `only_here` 一项就拿 0.40，单一维度可以独撑发布线。今天真实行的形态：

| 组合 | 算分 | v2 判定 | 按提示词自己的定义 |
| --- | ---: | --- | --- |
| `only_here + me_later + days + imp 4` | 0.7375 | 发布 | 「只有我以后会用 + 几天就过期」= 该拦 |
| `only_here + me_later + weeks + imp 4` | 0.7975 | 发布 | 同上 |

修复：算分过发布线后增加第 5 步**发布下限**——`reuse_audience >= team_or_stakeholders` 且
`validity_horizon >= weeks`，任一不足降为 `shadow`，reason `reuse_radius_below_minimum`，
保留算分与 shadow payload（下限只证明复用半径不够，不证明内容冗余，影子副本还要承担 14 天
窗口内的去重）。两个下限是枚举型偏好 `bake.knowledge_min_publish_audience` /
`bake.knowledge_min_publish_horizon`，取值必须落在对应维度梯上，拼错或来自旧版本取值时回落
默认而不是当成「无下限」：配置错误只允许削弱严格性，不得放大成误拦。

实测（`ai-sidecar/scripts/measure_knowledge_v3_effect.py`，只读重算今天全部 58 条 v2 已发布行；发布线取 Core
当时存下的 `quality_score`，下限只看存下的维度取值，不依赖本地重算重要性）：

| 指标 | 值 |
| --- | ---: |
| 今天 v2 已发布行 | 58 |
| 新规则下仍发布 | 46 |
| 被发布下限拦下 | **12（20.7%）** |
| 拦下行的维度组合 | `only_here+me_later+weeks` 9、`only_here+team+days` 2、`only_here+me_later+months` 1 |

用户点名的 4341、4347、4350 都在这 12 条里。58 是本次测量时刻的条数，sidecar 仍在烘焙，
这个数字会随时间上涨。

剩余 46 条里最大的一组是 `partially_recoverable + anyone_same_domain + months_or_more`
（15 条，占今天的 25.9%）——受众与时效都取最高档，发布下限对它们是恒真的。这一组是缺陷 2
的靶子。

#### 缺陷 2：公共参考知识挤在 `irreplaceability` 一轴上，表达不出来

那 15 条与用户要求保留的关键事实在三个算分维度上完全同形，差别只在于**结论内容本身是不是
公开世界早就写好的**。15.10 已经证明让模型用 `irreplaceability` 承担这个差别是失败的：它把
「需要重新通读才能复原」一视同仁写成 `partially_recoverable`，而这既包括公共教科书内容，
也包括用户自己的 commit。

修复：新增独立的事实轴 `source_publicity`（`own_work_only` / `publicly_documented`），不进算分，
只作硬否决输入；同时把 `irreplaceability` 判据里「外部公共资料不得判 `authoritative_elsewhere`」
那条撤销，交给新轴表达。

**否决要求三个自报一致，不看单一轴。** 单轴版本先落地，随即被实测否定：对 7 条种子做全新
replay（`qwen3.5:4b`，每条 60–75s，结果存
`doc/evaluations/knowledge-gate-seeds-publicity-2026-09-07.json`），`publicly_documented` 只出现
1 次，唯一一次落在用户点名的正例 3804 上，把它打成 `timeline_only`。改成
`publicly_documented` 且 `irreplaceability != only_here` 且 `reuse_audience == anyone_same_domain`
后，对同一份 replay 记录做确定性重算：

| 种子 | 期望 | 单轴 v3 | 两轴 v3（现行） |
| --- | --- | --- | --- |
| 1206 | keep | published 0.925 | published 0.925 |
| 4196 | keep | published 0.8475 | published 0.8475 |
| 3804 | keep | **timeline_only（误杀）** | shadow `reuse_semantics_incomplete` |
| 4270 | block | shadow 0.6175 | shadow 0.6175 |
| 4273 | block | shadow（语义不全） | shadow（语义不全） |
| 4274 | block | published 0.745 | published 0.745 |
| 4275 | block | published 0.7825 | published 0.7825 |

这与 `transient_process_detail` 豁免 `only_here` 是同一套设计：自报取值互相矛盾时，不拿最低档
单独定生死。

同一次 replay 还量到模型漂移：4274 的 `validity_horizon` 从上一轮存量的 `weeks` 变成这一轮的
`months_or_more`，算分随之从 0.705 抬到 0.745 越过发布线。种子命中从上一轮的 6/7 掉到 4/7，
**不是规则变差，而是同一条内容两次推理拿到的维度不同**——这就是缺陷 3。

#### 出处否决的实际拦截面（如实记录，不承诺拦截率）

1. 今天 58 条 v2 存量行的快照里没有 `source_publicity`（v2 契约没这个字段），一律 fail-open，
   `vetoed_by_publicity = 0`。这是设计选择：若缺失即否决，本地推理漏一个字段就会清空整个
   知识页（同 15.7 的 `match_score` 退化教训）。
2. 把这一轴单独问一次（`ai-sidecar/scripts/probe_source_publicity.py`，`temperature=0`，一次只问出处这一轴），
   与生产七字段长提示对照：

   | 提问口径 | 7 条种子 | 今天 15 条 veto-eligible 行 |
   | --- | --- | --- |
   | 生产长提示（全新 replay，完整上下文） | 1 条 `publicly_documented`，唯一一次落在正例 3804 上 | 未测（存量快照无该字段） |
   | 窄提问，输入取标题 + 摘要 | 0 条 | 3 条（4312、4345、4351） |
   | 窄提问，输入只取结论句 `subject_key` / `predicate_key` | 不可比，见下 | 7 条（新增 4295、4317、4321、4349） |

   7 条种子都是 `knowledge-open-semantic-v1` 时代的行，content 快照里没有
   `subject_key` / `predicate_key`，脚本按标题回退，因此第三行对种子用的其实还是同一份文本，
   不能当对照使用。
3. 三个可直接读出的结论：
   - **同一根轴、同一批输入，问法决定答案。** 长提示里 3804 是 `publicly_documented`（错），
     单独问一次就回到 `own_work_only`（对）；把输入从「以用户为主语的摘要」换成「结论句」，
     真实流量上的命中率从 3/15 抬到 7/15。这说明出处轴不是没有信号，而是它在七字段长提示里
     被顺带填掉了。
   - **提问对象决定答案的偏向。** 摘要以「用户观看的 / 用户获取的…」为主语时，模型答的是
     「这件事是不是用户自己的活动」，而不是「这句话公开世界有没有写过」，于是系统性偏向
     `own_work_only`（4295/4305/4306/4307/4316 全是科普视频与公开教程，5/5 答
     `own_work_only`；换成结论句后 4295、4317、4321、4349 四条翻成 `publicly_documented`）。
   - **同主题的近重复行内部不一致。** 标题 + 摘要口径下 4312 与 4317（同一件事「激活值 vs
     权重」）一分为二、4349 与 4351（同为投机解码）一分为二；换成结论句口径后这两组各自一致，
     但 4295 与同主题的 4305/4306/4307/4316 仍然分裂。
4. 因此本轮不把出处否决当拦截率承诺：它是**窄而硬**的准入条件，宁可不触发也不误杀。今天那
   15 条公共技术知识按用户自己的补充需求（「看到的重要学术、理论、技术、科学知识也要纳入」）
   本就不该被这条否决整体拦掉，该拦的是它们的重要性与近重复，属缺陷 3 与后续跟进项。

#### 线上首批 v3 判定（写这段时新规则已经在跑）

21:00 之后客户端进程已加载新构建：`bake_artifact_audits` 里最早的
`knowledge-reuse-radius-v3` 出现在 21:03，`bake_knowledge.content` 快照从 4352 起开始带
`source_publicity`。截至本次测量共 8 条 v3 判定：

| 判定 | 条数 | 明细 |
| --- | ---: | --- |
| `published` | 2 | 4352（0.745，partially + team + months）、4353（0.885，only_here + team + weeks），两条都满足发布下限 |
| `shadow` | 5 | 4 条 `reuse_semantics_incomplete`、1 条 `below_publish_score` |
| `timeline_only` | 1 | `redundant_public_reference`：timeline 10383「用户在 Google Gemini 中询问激活值与权重的区别及显存占用」，重要性 4 |
| `reuse_radius_below_minimum` | 0 | 还没有出现「过发布线但低于下限」的线上候选，缺陷 1 这条通道目前只在离线重算里生效 |

那条被出处否决拦下的正是用户要拦的一类：公共原理问答，与已发布的 4312、4345 同主题；它也是
第一期到第二期以来第一条被硬否决挡掉的公共参考知识（15.10 记录过三条硬否决零触发）。两点同时记下：

- 8 条样本太小，不能当拦截率用。
- 现在无法从审计区分当时跑的是单轴还是两轴构建——硬否决按设计不存 payload 快照，而
  `decision_reason_summary` 回落的又是模型自报的 `irreplaceability_reason`。要事后归因某次
  否决用了哪几个自报取值，需要补一条「把触发否决的维度写进 reason_summary」的小改动，本轮未做。

#### 缺陷 3：模型自报维度不稳定，是当前判定精度的天花板

三处独立证据指向同一件事，本轮**未修复**，只把口径写清：

- 同一内容两次推理的 `validity_horizon` 漂移一档（4274：`weeks` → `months_or_more`），直接把
  它从 shadow 推过发布线。
- 3804 的 `source_publicity` 在长提示里是 `publicly_documented`，在窄提问里是 `own_work_only`。
- 同主题近重复行的出处答案一分为二（标题口径下的 4312/4317、4349/4351；结论句口径下的
  4295 与 4305/4306/4307/4316）。

维度塌缩（15.10 的 `only_me_this_session` 0/38、`hours` 0/38）与 schema 不执行（15.11）已经
说明这不是提示词措辞能收住的误差。任何只依赖模型自报的门禁，其精度上限都由这条决定。
**用户已决定本轮不修复缺陷 3。** 两轮里提过并被明确否掉的五个方向一并记下来，避免重提：
二次独立复审、真实复用信号上浮（上一轮），拆轴窄调用、来源事实核验、排序配额制（本轮）。
若以后重开，必须先拿出能改变判定精度的实测证据，而不是先上机制。
`ai-sidecar/scripts/probe_source_publicity.py` 的两种提问口径（标题 + 摘要 / 只取结论句）保留
在仓库里，就是为这个判定准备的对照数据。

#### 生效边界

- 规则版本升 v3 只影响**新增**判定；今天 58 条 v2 行不重算、不降级、不隐藏（15.8 的存量边界
  不变）。用户已明确确认：存量保持不动，不按 v3 重判。
- 新契约与镜像改动需要 sidecar 重启才生效，Core 的判定改动需要重新编译并重启客户端进程。
  本轮写到这里时这两件事已经发生：21:03 起的审计行就是 `knowledge-reuse-radius-v3`（见上）。
  后续如果发现判定又回到旧口径，先看 `gate_rule_version` 分布——回到 `v2` 就是客户端跑回了旧
  构建，不是规则被改坏了。
