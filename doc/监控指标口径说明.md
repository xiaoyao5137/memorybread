# 监控指标口径说明

本文用于统一说明监控页中的采集可靠性、`入索引`、`向量化率`、`知识化率`、`知识挂载率`。

## 0. 采集可靠性

监控页的“采集实际间隔”“最近有效关键帧”和“当前内容空窗”来自独立的 `capture_attempts` 审计记录，不再用相邻 `captures.id` 或创建时间反推采集器是否工作。

- `captured`：产生了新的截图或可访问性文本记录。
- `continuity`：定时兜底发现内容与上一帧重复，但仍保留轻量 capture，并复用同一截图文件块。
- `deduplicated`：交互或上下文信号触发了视觉探针，但画面变化低于阈值；只保留审计，不生成 capture。
- `privacy_skipped`：命中系统隐私、应用黑名单或敏感内容规则。仅记录时间、结果和原因，不记录应用名、窗口标题、截图或文本。
- `degraded`：休眠、空闲、内存保护、队列拥堵等运行条件导致本次未保存内容。
- `failed`：截图、存储或其他采集步骤失败。

“当前内容空窗”从最近一次 `captured`、`continuity` 或 `deduplicated` 内容证据开始计算；电脑空闲或屏幕休眠时仍显示时长，但不标为异常。压力降级时周期会动态放宽，正常活动状态下最大目标间隔为 120 秒。采集尝试审计与采集记录使用相同保留周期。

### 交互信号与视觉门禁

采集器把应用切换、浏览器 URL 变化、键盘活动后停顿、点击和滚动组成触发信号群：

- 应用切换和 URL 变化立即进入视觉判断。
- 键盘、点击、滚动先聚合；连续活动停止 3 秒后触发，持续活动最长每 5 秒触发一次。
- 键盘监听只接收“发生过按键活动”这一事件类型，不读取、不传递、不保存键码、字符或输入文本。
- 触发后只在内存中抓取一帧，以 4×4 分块 dHash 判断局部和整体变化；低于阈值时记录 `deduplicated / visual_fingerprint_below_threshold`，不编码图片、不写 capture、不执行 OCR。
- 超过阈值时复用同一内存帧继续采集；只有 AX 正文不足时才编码截图并进入 OCR，避免二次截图。
- 视觉探针不可用时，为避免重要现场完全丢失，会记录降级原因并回退到原采集链路。定时兜底和手动采集不受视觉门禁拦截。

## 1. 统计范围

以下指标默认都基于监控接口的时间范围参数（如 `1d` / `7d` / `30d`）计算。

在当前实现中，知识与向量化链路并不是对所有 `captures` 生效，而是只面向“可处理 captures”。

### 可处理 captures（eligible_count）

满足以下条件的 capture 会被计入“可处理 captures”：

- 在当前统计时间范围内
- `is_sensitive = 0`
- 且至少存在一种可处理文本：
  - `ocr_text` 非空，或
  - `ax_text` 非空

公式：

```text
eligible_count =
  count(captures in range
    where is_sensitive = 0
      and (ocr_text != '' or ax_text != ''))
```

说明：
- 敏感数据不会进入向量化/知识提炼链路，因此不应作为这些比率的分母。
- 没有 OCR/AX 文本的记录也无法进入这两条处理链路，因此同样不计入分母。

## 2. 入索引（vectorized_count）

### 含义

入索引表示：**已经成功写入 `vector_index` 的 capture 数量**。

它是一个数量值，不是百分比。

### 公式

```text
vectorized_count =
  count(distinct capture.id
    join vector_index on vector_index.capture_id = capture.id
    where capture ∈ eligible_count 的集合)
```

也可以理解为：

```text
入索引 = 已完成 embedding 且已写入向量索引的 capture 数
```

### 解释

一个 capture 只有在 embedding 成功、并且向量结果成功写入 `vector_index` 后，才算“入索引”。

---

## 3. 向量化率（vectorization_rate）

### 含义

向量化率表示：**可处理 captures 中，有多少已经完成向量化并成功入索引**。

### 公式

```text
vectorization_rate = vectorized_count / eligible_count
```

即：

```text
向量化率 = 已入索引数量 / 可处理 captures 数量
```

### 解释

这个指标反映的是 `capture -> embedding -> vector_index` 这条链路的完成度。

理想情况下，如果后台处理器持续稳定运行，向量化率会逐步接近 100%。

---

## 4. 知识化率（knowledge_generation_rate）

### 含义

知识化率表示：**可处理 captures 对应的数据中，已经生成出多少条 `knowledge_entries`**。

它关注的是“是否产出 knowledge 条目”。

### 公式

```text
knowledge_generated_count =
  count(distinct captures.timeline_id
    where captures ∈ eligible_count 的集合
      and captures.timeline_id is not null)

knowledge_generation_rate = knowledge_generated_count / eligible_count
```

即：

```text
知识化率 = 可处理 captures 归属到的知识条目（timeline）数量 / 可处理 captures 数量
```

### 解释

知识提炼并不是一条 capture 对应一条 knowledge。通常是一组相关 captures 被合并后，生成一条 knowledge。

因此：
- 知识化率天然通常会低于向量化率
- 它更接近“知识沉淀效率”而不是“处理完成率”

---

## 5. 知识挂载率（knowledge_rate）

### 含义

知识挂载率表示：**可处理 captures 中，有多少已经成功回填了 `timeline_id`**。

它关注的是“capture 是否已经挂到某条 knowledge 上”。

### 公式

```text
knowledge_linked_count =
  count(captures ∈ eligible_count 的集合
    where timeline_id is not null)

knowledge_rate = knowledge_linked_count / eligible_count
```

即：

```text
知识挂载率 = 已关联 timeline_id 的 capture 数 / 可处理 captures 数量
```

### 解释

如果 5 条 captures 最终合并成 1 条 knowledge：
- 知识化率会增加 1
- 知识挂载率会增加 5 / eligible_count

因此知识挂载率通常会高于知识化率。

---

## 6. 三者关系

这几个指标关注的是不同层面：

### 向量化率
看的是：

```text
capture -> embedding -> vector_index
```

### 知识化率
看的是：

```text
一组 captures -> 1 条 knowledge_entries
```

### 知识挂载率
看的是：

```text
capture -> timeline_id 已回填
```

通常可以预期：

```text
向量化率 >= 知识挂载率 >= 知识化率
```

但在短时间窗口内，也可能因为后台处理延迟、分组尚未成熟等原因出现暂时波动。

---

## 7. 示例

假设某个时间范围内：

- 可处理 captures = 100
- 入索引 captures = 90
- 生成 knowledge_entries = 12
- 已挂载 timeline_id 的 captures = 40

则：

```text
入索引 = 90
向量化率 = 90 / 100 = 90%
知识化率 = 12 / 100 = 12%
知识挂载率 = 40 / 100 = 40%
```

这个例子说明：
- 向量化率衡量 embedding/索引链路
- 知识化率衡量知识条目产出
- 知识挂载率衡量 capture 被知识系统消化吸收的程度
