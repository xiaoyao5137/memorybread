# 技能模块设计与自测

## 1. 目标与范围

“技能”是桌面端统一的用户名称；内部接口和数据表继续沿用 `creation_skill`，以保持向后兼容。技能既可以把既有文档沉淀成可复用写作方法，也可以直接导入符合 Codex 规范的技能目录。文档沉淀覆盖两类来源：

- 方案创作记录；
- Bake 中已经生成的完整文档。

用户点击“沉淀技能”后，MemoryBread 在本机分析文档，自动产出并持久化可编辑的技能草稿。草稿首先包含面向智能路由的 `skill_description`：说明 Skill 解决的问题、可创作的文档类型、涉及领域和可验收产物；其次包含面向智能执行的 `execution_steps`：按先后顺序说明每一步目标、产出及可调用的 Agent、Skill、Tool；最后保留标题设计风格、行文设计思路、图片生成方式和话术表达风格等源文档风格指纹，并额外生成一份使用全新虚构主题的完整 Markdown 示例文档。完整示例目标篇幅为一千二百至两千二百个中文字符，至少包含摘要、六个承担不同内容角色的二级章节和结论，核心章节用完整段落实际复现提炼出的写法；低于完整度门槛的模型结果由确定性长示例替换。标题示例以源文档子标题为母版，只替换敏感主语、宾语、专名、数字与事实，尽量保留词序、动词、虚词、标点和长短；连续重复占位词或只剩占位词的标题会被过滤。其它字段同样必须给出可回溯到源文档的具体风格依据，不能退化为通用写作建议。系统同时根据原文自动推荐完整四级创作类目。用户显式保存后，技能才从草稿转为已保存；已保存技能默认不安装，可由用户安装、用于创作或公开到技能市场。

## 2. 核心流程

1. 用户从方案创作结果、创作记录或 Bake 文档点击“沉淀 Skill”。
2. 桌面端先请求 Core Engine 建立本机分析任务，再通过短请求轮询状态；Core Engine 在后台将原文只转发给本机 Creation Sidecar。这样即使本地模型推理超过 WebView 长连接等待时间，任务仍会继续到完成；旧的同步分析接口保留用于向后兼容。
3. Sidecar 优先使用本地文本模型生成结构化分析；提示词要求同时提炼能力描述、三至八步执行工作流、风格指纹、逐字段独立示例和完整示例文档。Agent 与 Tool 只能使用创作运行时的稳定标识；没有必要的资源数组必须留空，避免把所有能力机械堆入工作流。标题规则必须包含“可观察特征、句式骨架、适用位置或边界”，行文思路必须覆盖开篇、章节递进、段内顺序、列表条件、信息密度、过渡和收束。本地模型不可用、输出过短或结构不完整时使用确定性启发式分析：依据文档类型和正文线索补出“收集上下文 → 可选调研/分析/方案设计 → 撰写 → 审校”，且不会把源标题或原章节直接写入兜底结果。
4. 分析界面展示确定性百分比进度；分析结果立即以 `draft` 状态自动保存，后续编辑也会防抖保存。
5. 用户在编辑器中修改能力目标、适用文档、解决问题、涉及领域、目标产物和有序执行步骤；每个步骤可以选择受控 Agent、受控 Tool，并填写要协同的其它 Skill。用户也可以继续修改风格字段、二级说明标题、逐字段示例和完整示例文档，并确认系统推荐的完整四级类目。Skill 的任何字段都只能描述可复用方法，禁止带入具体公司、部门、事业部、团队、项目、产品、系统、客户、人员、日期、指标或金额。
6. 用户点击“保存技能”后状态变为 `saved`，此时仍为未安装；只有已保存技能可以安装。
7. 创作指令框输入 `@` 可以选择已安装技能；未显式选择时，客户端会把用户要求与 Skill 的能力目标、适用文档、解决问题、领域、交付物、原有简介、标题特征和类目共同评分。能力描述因此既是给人看的说明，也是给创作智能体使用的触发契约。
8. 命中的技能会把能力描述、执行工作流、完整类目、标题设计风格、行文设计思路、图片生成方式、话术表达风格、逐字段示例和完整示例文档注入本次真实生成请求。明确 Skill 的 `execution_steps` 是本轮唯一初始执行契约：Creation Agent 严格按声明顺序执行，只调度步骤中明确列出的受控 Agent 和已启用 Tool，不叠加路由模型推荐、内置模板、章节设计、文档撰写、质量审校或专项润色。唯一的反馈依赖例外是：步骤声明的 `data_search` 命中实时报表 URL 后，Harness 可在同一步追加受控 `webpage_scrape`，先取得当前快照再交回 Creation Agent；不会隐式追加数据分析 Agent。没有声明子 Agent 的步骤由 Creation Agent 自己完成，并按步骤标题顺序组装 Markdown；Skill 明确声明 Writer 或质量 Agent 时才交给对应 Agent。没有结构化步骤的明确 Skill 也只由 Creation Agent 执行，不进入通用子 Agent 链路。示例只作为 few-shot 学习结构与表达，不允许照抄示例主题；Skill 不得虚构业务事实。旧协议中的 `title_style` 继续作为 `common_titles` 的兼容镜像保存，但不再作为独立规则展示或注入。
9. 用户也可以在“技能”页选择一个 Codex 技能文件夹上传。目录根部必须有 `SKILL.md`，其 YAML frontmatter 必须包含合法的 `name` 和 `description`，且 `name` 与文件夹名一致；其余 `scripts/`、`references/`、`assets/` 和自定义文件按相对路径原样保存在本机。使用技能时，`SKILL.md` 和可读取的文本引用文件会在上下文上限内一同注入；脚本只作为文件保存和说明阅读，MemoryBread 不执行脚本。
10. 技能详情展示完整文件列表，可预览 UTF-8 文本和图片，并下载当前文件。原有结构化技能会即时合成一份标准 `SKILL.md`，因此所有技能都能通过同一个文件视图查看。
11. 用户在“技能”页点击“发布”时，客户端才把当前结构化技能上传到市场；发布成功后操作切换为“取消发布”，下架后仍保留本地技能和云端幂等标识，之后可以重新发布。手工上传的目录首期只保存在本机，不提供编辑或市场发布，避免丢失不属于结构化协议的文件。
12. 客户端内置技能市场，直接调用公开列表接口搜索、分页、查看详情并安装，不要求跳转官网。安装只下载市场已经公开的结构化技能内容，并以 `source_kind=market` 保存为本地只读来源副本。
13. 编辑器只负责修改和保存用户从本地文档沉淀的技能，不提供发布入口；已发布技能编辑后，需要回到“技能”页再次点击“发布”来更新市场版本。市场来源副本不显示编辑或发布操作，避免把其他作者的技能当作本人作品更新。

### 2.1 智能调用契约

| 字段 | 决策用途 | 约束 |
| --- | --- | --- |
| `skill_description.purpose` | 判断 Skill 为谁、在什么场景解决什么问题 | 必填，最多一千二百字 |
| `document_types[]` | 与用户要求的交付文档类型匹配 | 一至十二项 |
| `problems[]` | 与用户表达的问题、任务和决策目标匹配 | 一至十二项 |
| `domains[]` | 补充行业、职能或专业领域信号 | 可为空，最多十二项 |
| `deliverables[]` | 明确执行完成后的可验收产物 | 一至十二项 |
| `execution_steps[]` | 决定主 Skill 的实际执行顺序 | 最多十二步；新分析通常三至八步 |
| `execution_steps[].agents` | 本步骤可编排的专业 Agent | 仅接受运行时受控标识；与 Tool 合计每步最多四项 |
| `execution_steps[].tools` | 本步骤可调用的 Tool | 仅执行用户已启用且运行时认识的 Tool；与 Agent 合计每步最多四项 |
| `execution_steps[].skills` | 本步骤希望协同的其它 Skill | 以稳定标识或名称解析本机已安装 Skill；解析成功后自动随本轮请求进入环境，未知引用安全忽略 |

旧本地记录或旧市场 JSON 没有上述字段时，读取层会根据标题与简介补齐能力描述，并生成“收集需求与事实、撰写完整文档、审校并交付”三步兼容工作流，不要求用户重新沉淀。

## 3. 四级类目模型

产品描述中的“一二级行业、三级工种、四级具体分类”实际对应四级树，因此实现按四级建模：

| 级别 | 含义 | 示例 |
| --- | --- | --- |
| 一级 | 行业 | 互联网、金融、制造、医疗健康、教育、建筑地产、农林牧渔等 20 类 |
| 二级 | 细分行业 | 电商零售、云计算与 AI、医院与基层医疗、工程建设、航空运输等 94 类 |
| 三级 | 工种/角色 | 产品经理、架构师、临床医师、工程项目经理、科研人员等 199 类 |
| 四级 | 具体文档类型 | 产品需求文档、临床诊疗路径、施工组织设计、科研项目研究方案等 375 类 |

服务端只接受启用状态的第四级叶子类目。类目使用稳定 `key` 和 UUID，新增类目通过扩展迁移完成。客户端保留同 ID 的完整离线目录，云端接口不可用时仍能选择和自动推荐类目。

## 4. 数据边界与隐私

本模块遵循 Local First：

- 原文、来源类型、来源 ID、草稿/保存/安装状态保存在本地；
- 手工上传目录的全部文件以 Base64 内容和相对路径保存在本地数据库，并随资产快照备份恢复；单包最多 128 个文件、总计 10 MB，单文件最多 5 MB，`SKILL.md` 最多 512 KB；
- 从市场安装时，本地只保存公开 Skill 的结构化内容、云端 Skill ID 和 `market` 来源，不保存作者私有来源信息；
- 分析请求只访问本机 Core Engine 和本机 Sidecar；
- 首次发布后，云端只接收标题、简介、四级叶子类目和结构化 Skill 内容；
- 发布请求不包含原文、来源 ID、来源类型、本地引用、模型名、供应商密钥或模型成本；
- 提炼后会检查明显组织线索和大段原文重合；命中时使用安全通用兜底，不把可疑值写入 Skill；
- 客户端离线兜底不会使用源文档标题，也不会直接复制源章节名；章节只归并为“背景与目标”“总体方案”“实施计划”等通用角色；
- Admin API 发布校验会以 `SKILL_CONTENT_NOT_GENERALIZED` 拒绝仍含具体组织线索、日期或指标的内容或示例；
- 服务端 `POST /v1/creation-skills` 拒绝 `published=false`，防止客户端误把私有草稿上传；
- 公开列表和详情只查询 `published_at is not null` 且未删除的数据；
- Outbox 审计事件只记录 Skill ID 和作者用户 ID，不复制内容。

本地 Skill 已纳入 MemoryBread 资产快照，跨设备恢复时可恢复 Skill 生命周期；公开状态由 `cloud_skill_id` 和本地状态共同记录。旧快照没有 `status`/`installed` 字段时仍可兼容恢复。

## 5. 本地接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/creation/skills/analyze/jobs` | 建立本机文档技能分析任务，立即返回 `job_id` |
| `GET` | `/api/creation/skills/analyze/jobs/:job_id` | 读取分析任务状态及完成结果 |
| `POST` | `/api/creation/skills/analyze` | 同步分析来源文档，保留用于旧客户端兼容 |
| `GET` | `/api/creation/skills` | 获取本地技能；可按 `source_kind` + `source_id` 或 `installed` 筛选 |
| `POST` | `/api/creation/skills` | 新建本地技能（分析流程写入 `draft`，目录导入写入 `imported`） |
| `GET` | `/api/creation/skills/:id` | 获取本地技能详情和目录文件 |
| `PUT` | `/api/creation/skills/:id` | 更新草稿、保存、安装或公开状态 |
| `DELETE` | `/api/creation/skills/:id` | 软删除未公开的本地 Skill |

## 6. 云端接口

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| `GET` | `/v1/creation-skill-categories` | 公开 | 获取全部启用类目 |
| `GET` | `/v1/creation-skills` | 公开 | 搜索、类目筛选和分页 |
| `GET` | `/v1/creation-skills/:id` | 公开 | 获取已发布详情 |
| `GET` | `/v1/me/creation-skills` | 登录 | 获取当前作者的 Skill |
| `POST` | `/v1/creation-skills` | 登录 | 首次公开；按作者和本地 key 幂等 |
| `PUT` | `/v1/creation-skills/:id` | 作者 | 编辑、重新公开或下架 |

主要业务错误码：

- `CREATION_SKILL_PUBLISH_REQUIRED`：首次提交未确认公开；
- `INVALID_CLIENT_SKILL_KEY`：本地幂等标识不合法；
- `INVALID_SKILL_TITLE` / `INVALID_SKILL_SUMMARY`：标题或简介不合法；
- `INVALID_SKILL_CONTENT`：结构化内容不完整或超长；
- `SKILL_CONTENT_NOT_GENERALIZED`：字段或示例仍包含具体组织线索、日期或指标，需要改写为通用表达；
- `INVALID_SKILL_CATEGORY`：类目不存在或已停用；
- `SKILL_CATEGORY_NOT_LEAF`：没有选择第四级具体文档类型；
- `CREATION_SKILL_NOT_FOUND`：详情不存在、未公开或不属于当前作者。
- `CREATION_SKILL_MARKET_INITIALIZING`：服务已部署但市场表尚未迁移；公开读取返回空市场，写操作返回可识别的 503。

## 7. 页面与交互

桌面端：

- 方案创作结果和每条创作记录都提供“沉淀技能”；
- Bake 文档详情提供“沉淀技能”；
- Bake 文档和方案创作结果都会展示按来源查询到的关联技能，点击默认打开只读详情，需要修改时再从管理卡片进入编辑器；
- 创作面板增加“技能”页签，集中管理草稿、已保存、安装与发布状态；“我的技能”支持选择 Codex 技能文件夹上传；卡片标题和“查看详情”都能打开只读详情和文件视图；
- 删除未发布技能时先展示包含技能名称和不可恢复提示的二次确认；取消、点击遮罩或按 `Escape` 均不会删除；
- “技能市场”子页提供客户端内搜索、分页、作者与完整类目展示、详情预览和安装操作；已安装项明确显示状态并禁止重复安装；
- 编辑器展示“正在本机分析文档写法”的阶段文案、确定性百分比进度条、自动草稿状态、四级级联选项卡和全部可编辑内容，只保留保存操作；能力描述区可以编辑目标、文档类型、问题、领域和产物；执行工作流区可以增删步骤、调整文字并选择每步 Agent/Tool、填写协同 Skill；四个风格字段固定为“标题设计风格”“行文设计思路”“图片生成方式”“话术表达风格”；每个字段下展示并允许编辑基于源文档风格、但完成敏感主客体替换的示例，末尾展示完整示例文档；
- 创作输入框支持 `@` 已安装 Skill 选择器，并展示“@ 已选择”或“自动匹配”的本次使用标签；
- 已发布 Skill 在桌面端暂不提供删除操作，避免官网出现失去作者控制的孤儿内容。

官网：

- 导航增加“创作市场”；
- `/creation-skills` 提供专题头图、搜索、四级类目筛选和 Skill 卡片；
- `/creation-skills/[id]` 展示作者昵称、完整类目路径、能力描述、有序执行工作流、资源标识、两层标题、逐字段示例及完整示例文档；
- 页面使用服务端动态渲染，发布或下架后无需重新构建站点。
- Admin API 与官网兼容“官网先于数据库迁移完成”的部署窗口：此时展示正常空态，不再显示“创作市场暂时无法读取”。

## 9. 部署顺序

1. 桌面端随 Core Engine 启动执行 `076_remove_creation_skill_structure_pattern.sql`：删除旧 `structure_pattern` 列，并清理 `section_headings`、`field_examples` 中未展示的同名历史键；其余 Skill 数据保持不变。
2. 云端 MySQL 执行 `0004_remove_creation_skill_structure_pattern.sql`，清理已有市场 Skill 的顶层及嵌套历史键；初始化官方 Skill 时同样在写入前剔除这些键。
3. 部署 Admin API，验证公开列表、详情和鉴权写接口。
4. 部署官网，开放“创作市场”入口。
5. 发布带有本地迁移 `076_remove_creation_skill_structure_pattern.sql` 的 MemoryBread 客户端与 Sidecar。

按此顺序部署时，新服务端对旧客户端保持兼容；新客户端只有在用户主动公开时才依赖新云端接口。即使官网/Admin API 先部署，公开读接口也会返回空市场而不是数据库错误；迁移完成前写接口会明确返回 503，避免误报成未知保存失败。
