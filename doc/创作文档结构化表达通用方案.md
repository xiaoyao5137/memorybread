# 创作文档结构化表达通用方案

**状态：** 待评审
**负责人：** 未指定
**决策人：** 待明确
**最后更新：** 2026-08-22

## 摘要

创作页面已经支持 Markdown 标题、加粗、列表和表格，但生成链路只约束“写什么”，没有统一约束“这类信息应该怎样表达”。结果是模型即使输出了多个标题，也常在章节内连续堆叠段落或同级列表，缺少父子关系、重点和阅读节奏。

本方案引入一套跨普通创作与 Skill 创作共用的“文档表达协议”：章节设计阶段先为内容选择语义块，撰写阶段按语义块生成标准 Markdown，确定性质检识别平铺叙事并按需触发结构润色，页面最后按统一设计令牌渲染。首期不引入富文本编辑器或私有文档 AST，继续以 Markdown 为存储和导出格式。

## 问题与证据

### 最近一次创作记录

2026-08-22 00:58 生成的创作历史第 89 条《GPU成本优化周报》具有以下特征：

- 文档有一个一级标题、四个二级章节及部分三级标题，说明基础标题渲染并非缺失。
- “会议纪要”将不同主题全部放在同一层无序列表；“AIGC进度总结”虽有三级标题，但每个三级标题内部仍是同一层列表。
- “GPU算力数据”包含三个连续短段落，原本适合对比或父子归类的信息仍以平铺文字呈现。
- 该记录使用“GPU成本优化周报模板”的严格 Skill 流程。严格流程直接按四个 `execution_steps` 拼装章节，在计划构建阶段提前返回，因此不会执行通用 `chapter_design_agent` 和 `quality_review_agent`。
- 当前质量检查只验证标题数量、章节长度、表格合法性和加粗比例等指标，没有检测章节内部的父子层级、连续平铺段落、列表项同构性或表达形式是否与信息关系相符。

页面现有 Markdown 组件已经为 H1、H2、H3 设置了 26、20、16 像素字号，并为 `strong` 设置了品牌色、字重和下划线。因此本问题不能仅通过增大字号解决；生成、质检和渲染必须共享同一套结构语义。

### 用户影响

- 用户需要逐句阅读，难以通过扫读直接找到结论、数据、风险和行动项。
- 同一层级同时承载主题、事实、动作和结果，读者难以判断它们之间是并列、包含、顺序还是因果关系。
- Skill 创作与普通创作的版式质量不一致，同一类文档会因执行路径不同而表现不同。
- 后续复制到飞书、Markdown 编辑器或导出时，结构问题会被原样带走，页面局部 CSS 无法补救。

## 目标与结果

- 同一套规则覆盖普通创作、严格 Skill 创作、续写修订和历史文档展示。
- 每个章节根据内容关系选择最合适的段落、父子列表、步骤、表格、引用块或图示，不以“形式丰富”为目标强行套组件。
- 标题层级、重点强调和列表缩进在创作页、复制内容和 Markdown 导出中保持一致。
- 质量门禁能识别典型平铺问题，并只重写相关章节，不破坏事实、数据口径、来源和 Skill 章节白名单。
- 发布后可观测结构质量改善，并能安全回退到现有 Markdown 生成方式。

## 非目标

- 首期不建设 Notion/飞书式富文本编辑器，不改变 `generated_content` 的 Markdown 存储格式。
- 不要求每个章节都使用列表、表格或图示；连续论证、背景解释和因果分析仍应使用段落。
- 不把视觉多样性当作质量，不自动插入图标、彩色卡片、装饰分隔线或无信息量的图。
- 不根据内容样式推断新事实，不为凑齐层级虚构父项、子项、数字或状态。
- 不在客户端暴露模型供应商、密钥、成本或路由信息。

## 用户与场景

### 文档创作者

- 用户生成周报、方案、总结、复盘或分析文档，希望首版即可扫读和汇报，而不是再手工重排层级。
- 用户使用自定义 Skill 限定章节与取数步骤，希望 Skill 结构继续生效，同时获得统一的章节内表达质量。
- 用户通过对话修订某个章节，希望只调整目标章节的表达形式，其他内容和事实不被重写。

### 文档读者

- 读者先浏览标题和加粗标签，再按需展开具体事实；阅读路径应在不看全文时仍可理解。
- 读者需要区分并列主题、父子归属、执行顺序、指标对比和因果解释。

## 核心设计

### 一、定义“内容关系”，再选择“展现方式”

每个章节在生成正文前，必须识别其中的内容关系。表达形式是关系的结果，而不是随机的排版装饰。

| 内容关系 | 默认展现方式 | 使用条件 | 不应使用的情况 |
| --- | --- | --- | --- |
| 单一判断及其论证 | 短段落 | 需要解释原因、边界或推导 | 多个可独立扫描的同层事项 |
| 并列事实、动作或结论 | 无序列表 | 至少两个同语法、同口径的项目 | 项目存在明确先后顺序 |
| 主题与明细、对象与属性 | 两级父子列表 | 父项可概括至少两个真实子项 | 只有一个子项，或父项只是换句话重复子项 |
| 流程、优先级或时间顺序 | 有序列表 | 顺序改变会影响理解或执行 | 只是并列事项 |
| 多对象、多属性比较 | 表格 | 至少三个对象且有两个以上统一比较维度 | 单元格需要长篇论证，或口径无法统一 |
| 结论、限制、风险提示 | 引用块加标签 | 内容需要从正文中被优先看到 | 普通背景描述或整段正文 |
| 三个以上节点的关系、流程或状态变化 | Mermaid/PlantUML | 文字难以准确表达关系 | 单一事实、简单步骤或装饰需求 |

### 二、统一 Markdown 表达规范

#### 标题

- `#`：全文唯一主标题；一篇文档只能有一个。
- `##`：一级章节，承担互斥的内容角色，如“本周进展”“关键指标”“风险与行动”。
- `###`：章节内真实子主题；只有存在至少两个独立内容块，或需要与相邻子主题对照时才使用。
- `####`：仅用于长文中的局部明细；默认不超过四级，不允许从 H2 跳到 H4。
- 同层标题应采用一致的语法结构，标题本身不再重复加粗。
- 标题字号与字重由页面设计令牌控制，模型不得输出内联 HTML、字号或颜色。

#### 加粗

- 加粗用于标签、关键数字、明确结论、风险和行动项，例如 `**已完成：**`、`**性能提升 52.2%**`。
- 不加粗整段，不对标题重复加粗，不为普通名词加粗。
- 默认每千字 3—8 处；该范围是质检提示阈值，不是强制配额。

#### 列表

- 并列列表项必须保持同一语法起点，如都以“动作对象：结果”或“状态：说明”开头。
- 父子列表最多两级；第二级相对父项使用统一缩进。
- 父项必须是可独立理解的真实分类或对象，不能只写“具体如下”“相关内容”等空父项。
- 单个父项只有一个子项时，优先合并为一个列表项或段落。
- 有序列表只表达步骤、阶段、排名或明确优先级，不能用编号装饰普通并列项。

#### 段落、表格和提示块

- 段落承担解释、因果和取舍；一个段落优先只表达一个中心判断。
- 表格前用一句话说明口径，表格后只补充无法放进单元格的例外或解释。
- 引用块采用 `> **结论：** ...`、`> **风险：** ...`、`> **限制：** ...` 等有限标签，页面渲染为克制的提示块。
- 不为了避免平铺而强制把所有内容改成列表；关系不清晰时优先保留段落。

### 三、引入通用“章节表达计划”

在创作运行环境中增加 `creation.document.presentation.v1`。它是生成过程中的语义计划，不替代最终 Markdown，也不要求历史记录迁移。

```json
{
  "schema_version": "creation.document.presentation.v1",
  "document_role": "weekly_report",
  "sections": [
    {
      "section_key": "weekly-progress",
      "title": "本周进展",
      "heading_level": 2,
      "purpose": "让读者按主题扫读本周完成项",
      "blocks": [
        {
          "block_key": "progress-by-topic",
          "relation": "parent_child",
          "presentation": "nested_unordered_list",
          "group_by": "工作主题",
          "emphasis": ["状态", "关键数字"]
        }
      ]
    }
  ]
}
```

稳定枚举建议如下：

- `relation`：`argument`、`parallel`、`parent_child`、`sequence`、`comparison`、`callout`、`network`。
- `presentation`：`paragraphs`、`unordered_list`、`nested_unordered_list`、`ordered_list`、`table`、`blockquote`、`diagram`。
- `emphasis`：只描述允许强调的语义角色，不指定颜色、字号或具体 CSS。

`section_key` 和 `block_key` 在单次运行内稳定，用于质检、局部修订和观测；不作为用户可见 ID，也不进入外部来源引用。

### 四、普通创作与 Skill 创作使用同一质量链路

```text
需求与证据
  → 章节骨架
  → 章节表达计划
  → Markdown 撰写/Skill 步骤组装
  → 确定性结构质检
  → 必要时局部结构润色
  → Markdown 渲染与导出
```

#### 普通创作

`chapter_design_agent` 在现有章节蓝图中增加每章的 `relation`、`presentation`、分组依据和强调对象。文档撰写 Agent 必须消费该计划，但在证据不足以支持父子关系时可以降级为段落或同级列表，并记录降级原因。

#### 严格 Skill 创作

严格 Skill 的 `execution_steps` 继续作为唯一章节白名单，不插入新章节，也不改变步骤顺序。在 `apply_skill` 后由确定性适配器把每个步骤的 `title/objective/output` 编译为章节表达计划：

- 明确写“列表展示”时映射为 `unordered_list`；若目标中存在可验证的分组维度，再映射为 `nested_unordered_list`。
- 明确写“表格展示”“对比”或列定义时映射为 `table`。
- 明确写“步骤”“流程”“优先级”时映射为 `ordered_list`。
- 没有明确形式时，根据内容关系选择；无法可靠判断时使用 `paragraphs`。

适配器只增加章节内表达约束，不增加事实、不调用新 Tool，也不突破 Skill 白名单。严格 Skill 完成组装后必须执行与普通创作相同的结构质检；这是文档质量门禁，不属于新增业务步骤。

#### 修订

用户要求“把这段整理得更清晰”“改成父子列表”时，编辑意图需要记录目标章节和目标表达形式。结构润色只修改对应章节；若用户没有指定形式，则重新运行该章节的表达选择，不重排全文。

### 五、增加确定性结构质检与局部修复

在现有 `_inspect_document_quality` 基础上增加以下可观察问题：

| 问题代码 | 检测信号 | 默认处理 |
| --- | --- | --- |
| `heading_hierarchy_invalid` | 多个 H1、标题跳级、空标题 | 文档结构润色 |
| `section_flat_narrative` | 长章节含多个并列信号，但只有连续段落且无子结构 | 文档结构润色 |
| `list_grouping_missing` | 同一列表存在重复类别标签，且每类至少两个项目，却全部平铺 | 文档结构润色 |
| `list_items_not_parallel` | 同级列表混合标题、完整段落、步骤编号和不同口径 | 文档结构润色 |
| `nested_list_invalid` | 超过两级、空父项、父项仅一个子项或缩进不合法 | 文档结构润色 |
| `presentation_mismatch` | 表达计划要求表格/步骤/父子列表，但输出没有对应结构且无降级记录 | 文档结构润色 |
| `emphasis_needs_polish` | 没有重点或强调比例过高 | 现有字体润色 |

确定性规则只负责发现候选问题，不能仅凭关键词自动改写事实关系。新增 `document_structure_polisher` 接收目标章节、问题证据和章节表达计划，输出完整 Markdown；应用补丁时沿用现有局部差异与未触及章节保护机制。

为减少误报，`section_flat_narrative` 和 `list_grouping_missing` 应满足多信号才触发，例如重复标签、相同语法起点、章节长度及表达计划至少命中两项。纯论证型章节即使有多个段落也不判为平铺失败。

### 六、统一页面渲染

将创作文档 Markdown 的内联样式迁移到 `.creation-document-body` 下的设计令牌和 CSS，保持 MemoryBread 现有白色卡片、浅灰背景、深色正文和克制品牌强调色。

| 元素 | 建议桌面样式 | 语义 |
| --- | --- | --- |
| H1 | 26px / 750 / 1.25 | 文档标题 |
| H2 | 20px / 720 / 1.35，上间距 28px | 一级章节 |
| H3 | 16px / 700 / 1.45，上间距 20px | 子主题 |
| H4 | 14px / 700 / 1.5 | 局部明细 |
| 正文 | 14px / 400 / 1.75 | 论证与解释 |
| 一级列表 | 左缩进 22px，项间距 6px | 并列主题 |
| 二级列表 | 左缩进 20px，项间距 4px，弱化项目符号 | 父项明细 |
| 引用块 | 左侧 3px 品牌色边线，浅色背景 | 结论、风险、限制 |

页面需要补充 `ul/ol`、嵌套列表、`blockquote`、H4 和表格的统一样式，并覆盖暗色模式。字号表达由标题层级决定，加粗表达由 `strong` 决定；两者不混用。复制和导出继续保留纯 Markdown 语义，不复制页面 CSS。

## 需求

- **FR-001** — 初次普通创作时，系统必须在正文生成前为每个章节形成包含内容关系和建议表达形式的章节表达计划。
- **FR-002** — 严格 Skill 创作时，系统必须在不新增、不删除、不重排 `execution_steps` 的前提下，为每个步骤形成章节内表达计划。
- **FR-003** — 文档撰写 Agent 必须按表达计划输出标准 Markdown；无法由证据支持计划结构时必须选择更保守的表达形式，且不得补造父子关系。
- **FR-004** — 系统必须对普通创作和严格 Skill 创作执行同一套确定性结构质检。
- **FR-005** — 结构质检命中可修复问题时，系统必须只调度文档结构润色能力处理相关章节，并保护未触及章节、事实、来源、数据口径和代码块。
- **FR-006** — 用户进行局部修订时，系统必须保留目标表达形式，并只更新目标章节，除非用户明确要求重排全文。
- **FR-007** — 创作页面必须按统一样式渲染 H1—H4、段落、两级列表、有序列表、表格、引用块和重点强调。
- **FR-008** — 复制、历史记录和 Markdown 导出必须保留生成内容的标题、列表层级、表格和强调语义。
- **FR-009** — 没有适合结构化表达的内容时，系统必须允许使用自然段落，不得为满足形式指标强行生成列表、表格或图示。
- **NFR-001** — 新增运行时 Python 必须兼容 Python 3.9，不得使用 Python 3.10 及以上专属语法。
- **NFR-002** — 结构质检不得把用户正文、来源正文、提示词或密钥写入日志；观测只记录结构计数、问题代码和耗时。
- **NFR-003** — 结构规划和质检失败时必须降级为现有 Markdown 生成与渲染链路，不得阻断文档交付。
- **NFR-004** — 首期结构规划与确定性质检的本地处理增量 P95 应低于 100 毫秒，不包含模型润色耗时。
- **NFR-005** — 页面结构样式必须支持键盘导航、系统字体缩放和暗色模式，且正文最小字号不低于 14px。

## 状态、失败与恢复

| 状态 | 行为 | 用户可见结果 |
| --- | --- | --- |
| `planned` | 已生成章节表达计划 | 正常继续，无额外确认 |
| `generated` | 已生成 Markdown | 流式展示当前文档 |
| `quality_passed` | 未发现结构问题 | 直接完成 |
| `quality_repairing` | 命中可修复问题 | Agent 轨迹显示“优化章节结构” |
| `quality_deferred` | 问题存在但缺少可靠分组依据或已达修复上限 | 保留当前文档，不虚构层级 |
| `fallback` | 计划解析、质检或润色失败 | 使用现有 Markdown 结果完成 |

结构润色最多一轮；同一问题再次出现时标记 `quality_deferred`，不循环重写。用户仍可通过对话明确指定分组方式继续修改。

## 接口与兼容性

- 在共享契约中新增可选的 `creation.document.presentation.v1` 定义；旧客户端和旧 Sidecar 不认识该字段时忽略，不影响现有创作请求。
- `presentation_plan` 保存在运行环境和 Agent 事件中时只包含章节标题、语义枚举和结构计数，不包含完整来源正文。
- `generated_content`、历史接口、复制和导出仍使用 Markdown 字符串，现有历史记录无需迁移。
- 现有 Skill 数据结构无需强制升级；新建或编辑 Skill 时可预览系统从 `execution_steps` 推导出的表达方式，但不要求用户手工填写新字段。
- 若未来需要稳定的富文本编辑和跨格式导出，可在不改变本轮语义枚举的前提下，将表达计划升级为文档 AST；该升级不属于首期范围。

## 验收标准

- **AC-001** — 验证 **FR-001**。给定一个无 Skill 的周报请求，当章节设计完成时，每个 H2 章节都有稳定 `section_key`，并至少声明一种 `relation` 和 `presentation`。

## 观测与效果评估

- **OBS-001** — `creation.presentation.plan.generated`：记录章节数、各表达形式计数、是否为严格 Skill，不记录标题和正文；用于判断协议覆盖率。
- **OBS-002** — `creation.structure.review.completed`：记录问题代码、问题数、是否触发修复、质检耗时；用于判断主要失败类型。
- **OBS-003** — `creation.structure.repair.completed`：记录修改章节数、修复前后结构计数、是否通过复检；用于判断自动修复有效性。
- **OBS-004** — `creation.document.user_reformat_requested`：仅记录用户是否在首版后提出“列表/层级/表格/排版”类修改及匿名意图类别；用于衡量首版返工率，不记录用户原文。
- **OBS-005** — 发布前以最近 30 条经过脱敏的结构统计建立基线，发布后比较“格式返工率”“结构质检一次通过率”和“修复后通过率”；具体成功阈值在取得基线后评审确定，不预设虚假目标。

## 分阶段发布、迁移与回滚

- **ROLL-001 — 契约与夹具：** 新增共享表达协议、最近 GPU 周报结构夹具和 Markdown 渲染夹具；此阶段不改变线上生成结果。
- **ROLL-002 — 生成约束：** 普通创作接入章节表达计划；通过功能开关小范围启用，异常时关闭开关回到现有 Writer 提示。
- **ROLL-003 — Skill 兼容：** 为严格 Skill 增加确定性表达计划适配器和统一质检；验证四个现有步骤不被新增、删除或重排。
- **ROLL-004 — 局部修复：** 启用 `document_structure_polisher`，限制一轮并沿用局部补丁保护；事实或章节保护测试失败即停用自动修复，仅保留质检观测。
- **ROLL-005 — 页面样式：** 将内联 Markdown 样式迁移为作用域 CSS，完成亮色、暗色、全屏、窗口窄屏和复制测试。
- **ROLL-006 — 全量：** 观察至少一个完整发布周期后再移除功能开关；回退只关闭表达规划和结构修复，不回滚历史 Markdown。

## 风险与缓解

- **误分组改变语义：** 模型可能把仅仅相似的事实归为父子关系。缓解方式是分组必须有证据或用户提供的维度，无法确认时降级为同级列表或段落。
- **过度结构化：** 为通过质检而把论证拆碎。缓解方式是将 `argument → paragraphs` 明确定义为合格表达，并要求平铺问题由多信号触发。
- **严格 Skill 被隐式改写：** 通用规则可能突破步骤白名单。缓解方式是表达计划只能注解步骤内部，不新增章节、Tool 或事实，并以步骤数量、标题和顺序做回归测试。
- **润色破坏数据和来源：** 结构修复可能改动数字或链接。缓解方式是复用现有文档补丁与未触及章节保护，并增加数字、URL、表格、代码块逐字保护断言。
- **Markdown 方言不一致：** 不同目标编辑器对嵌套缩进和引用块支持不同。缓解方式是只使用 CommonMark/GFM 子集，并用复制夹具验证。
- **长文额外耗时：** 新增模型润色会延迟完成。缓解方式是规划和质检尽量确定性执行，只有命中可修复问题才调用一次局部润色。

## 开放问题与待决策

- 首期是否把 `presentation_plan` 持久化进 `creation_history`，还是只保留在 `agent_trace_json`。前者利于复盘和修订，后者改动更小。
- 引用块首期是否只支持“结论/风险/限制”三类标签，避免形成第二套卡片组件系统。
- 新建 Skill 的编辑器是否展示“系统推导的表达形式”只读预览；这能提升可解释性，但不是生成质量的前置条件。
- 成功阈值需要在脱敏结构基线完成后由产品决策人确认。
